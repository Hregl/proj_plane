## 1 缺陷一：调度停顿后迟到到位可解除超时并继续发送 P2

**原因：** 队列只存文本，没有接收时刻。`_wait_for()` 到期后调用
`_drain_available()`，只要主线程在消费 `MOVE_ACCEPTED` 时被停顿，迟到
的 `ARRIVAL_OBSERVED` 就会被当成准时消息，令谓词为真，并继续发送 P2。

**修正：**

* reader 线程在读出一行后立即打 `time.monotonic()` 时间戳，队列元素为
  `(recv_at, line)`。
* P1/P2 分别记录 `arrival_deadlines[seq]`；到位行的 `recv_at` 晚于对应
  截止时间时只记入 `late_arrivals`、置 `timed_out`，不加入 `arrivals`。
* `_wait_for()` 把本次等待的 `deadline` 传给消费函数；接收时刻晚于
  deadline 的行进入 `deferred`，只留档，不满足本次谓词；等待到期前消费
  的行按接收时刻判断，不按“主线程何时处理”判断。
* 迟到行仍在日志中保留，供复核确认工具确实报过到位。

**修复前后（同一假进程、同一注入，仅换驱动）：**

| 项目 | 修复前 | 修复后 |
|---|---|---|
| 等待期限 / 到位时刻 | 50 ms / 150 ms | 50 ms / 150 ms |
| 主线程处理 `MOVE_ACCEPTED` 停顿 | 300 ms | 300 ms |
| `success` | `True` | `False` |
| `timed_out` | `False` | `True` |
| `arrivals` | `[1, 2]` | `[]` |
| 是否发送 P2 | **是** | **否** |
| `reason` | `ok` | `P1 timeout after 0.05s` |

## 2 缺陷二：读取解码失败被当成正常 EOF

**原因：** `_reader_main()` 在 `finally` 中无条件 `eof.set()`。无论正常
读到 EOF，还是 `readline()` 抛出 `UnicodeDecodeError`，驱动都看到
`eof_seen=True`，完整输出判据因此可通过。

**修正：**

* 正常读到空行才置 `eof`；`readline()` 抛异常时记录
  `reader_error`，不置 `eof`。
* 新增 `reader_done` 事件区分“reader 已结束”和“正常 EOF”；等待/退出
  收束可用 `reader_done`，成功判据只认 `eof`。
* 新增判据 `reader_ok`：只有 `reader_error is None` 才通过；失败原因明确
  写成 `reader failed: ...`。
* reader 异常会尽快传回主线程，驱动按失败路径停止/退出。

**修复前后（完整收尾行之后写入非法 UTF-8）：**

| 项目 | 修复前 | 修复后 |
|---|---|---|
| `success` | `True` | `False` |
| `eof_seen` | `True` | `False` |
| `reader_error` | `None` | `UnicodeDecodeError: ... 0xff ...` |
| `reason` | `ok` | `reader failed: UnicodeDecodeError: ...` |
| 收尾行是否已收到 | 是 | 是（但不能再据此判成功） |

## 3 缺陷三：日志写入异常跳过收尾，子进程仍在运行

**原因：** `_write()` 不处理 `OSError`，`run()` 的 `finally` 只关闭部分
文件资源。日志写入失败时异常直接抛出，没有发送 `stop`/`quit`，子进程
和 stdin 留在运行状态。

**修正：**

* `_write()` 捕获 `OSError`/`ValueError`，记录 `log_error`，不再让日志
  问题从收尾路径抛出；新增判据 `log_ok`。
* 主流程发现 `log_error` 后停止继续定位，但**仍执行** `stop` → `quit`。
* `run()` 对主流程异常（含受控注入的 `OSError`）统一捕获，记录
  `driver_exception`，随后执行有界收尾：`_stop_then_quit()` → 等待退出
  → 超时才强杀并回收；新增判据 `no_driver_exception`。
* 异常路径的结论仍通过返回的 `RunResult` 和 notes 文件报告，不以
  “抛出异常”代替失败记录。

**修复前后（P1 发出后，处理 `MOVE_ACCEPTED` 时注入一次 `OSError`）：**

| 项目 | 修复前 | 修复后 |
|---|---|---|
| 驱动是否抛出到调用方 | **是**（`OSError`） | 否，返回失败结果 |
| `success` | 无结果 | `False` |
| `reason` | 无 | `driver exception: OSError: injected log write failure` |
| 是否发送 `stop` | **否** | **是** |
| 是否发送 `quit` | **否** | **是** |
| 子进程运行后是否仍存活 | **是** | **否**（退出码 0，已回收） |
| 是否发送 P2 | 否（未执行到） | 否 |

## 5 判据变化与边界

新增成功判据 `reader_ok`、`log_ok`、`no_driver_exception`；原有判据
（两次到位、真实退出码 0、收尾行齐全、日志 `EXIT_CODE 0`、EOF、无超时/
强杀/工具终态）保持不变。两个退出码反例仍分别只对
`exit_code_zero` / `exit_code_line_zero` 敏感。

边界不变：

* `exit_hang` 的 0.3 s 只是离线测试配置；实机 `--exit-timeout` 必须覆盖
  工具自身停止与观测预算。
* 强杀只表示驱动未取得正常退出结果，**不表示设备已停止**。
* 收尾行齐全、EOF、退出码 0 只证明驱动完整收集退出结果；
  **“退出阶段零补帧”仍需逐帧核对**。

以上只证明驱动状态机与假子进程行为，不证明真实工具、真实退出阶段或
真实设备行为。P1/P2 原始证据、R2 方案偏离登记、T2 整体结论均不变；
本批不需要也未被授权重发实机定位命令。
