## 2 旧驱动的缺陷

旧驱动 `08_run_t2el.py`（作为已执行证据原样保留）存在以下问题：

1. `wait_until()` 用阻塞 `stdout.readline()`，所谓 `timeout_s` 只在两次
   读到行之间检查，读不到行时超时不能及时生效；截止时间用
   `time.time()`，不抗系统墙钟跳变。
2. 发出 `quit` 后只做 `proc.wait(timeout=10.0)`，随后在 `finally` 中
   立即关闭日志；工具在 `quit` 之后输出的 `USER quit`、`EXIT_STOP`、
   `FINAL`、`EXIT_CODE` 没有被继续收集到 EOF。因此
   `07_T2EL_two_moves.log` 缺少汇总行。
3. 成功判据只有 `P1/P2 ARRIVED`；没有要求工具退出码为 0，也没有要求
   `FINAL normal_exit=1` / `EXIT_CODE 0` 齐全。即使工具异常退出或收尾
   记录缺失，也可能打印成功。
4. 失败/超时路径的 `stop` 与 `quit` 之后没有统一的 EOF 收集；强制
   `kill()` 也没有被明确记录为失败原因。

## 3 新驱动的判据与实现

新驱动：`AircraftPoseSystem/tools/t2_acceptance_driver.py`。

| 要求 | 实现 |
|---|---|
| 可超时读取 | 独立 reader 线程读 stdout，主线程用 `queue.Queue.get(timeout=...)`；不再在控制流程中阻塞 `readline()` |
| 单调时钟 | 所有截止时间使用 `time.monotonic()`；驱动中不使用 `time.time()` |
| 停止/退出持续收集至 EOF | `quit` 后关闭 stdin，持续消费队列直到进程退出且 EOF；失败路径先 `stop` 再 `quit` |
| 两次到位 | 必须分别观察到 `ARRIVAL_OBSERVED seq=1` 和 `seq=2` |
| 工具退出码 0 | 必须 `proc.returncode == 0` |
| 正常收尾记录齐全 | 必须同时出现 `EXIT_REQUEST`、`EXIT_STOP`、`FINAL` 且 `normal_exit=1`、`EXIT_CODE 0` |
| EOF | 必须观察到 stdout EOF |
| 超时/强制终止判失败 | 等待到位超时、退出超时、`kill()` 均置失败标志；退出超时在杀掉进程后仍判失败 |

失败路径不会自动重发定位；驱动的输出日志保留原始工具行，并追加
`DRIVER_SEND`、`DRIVER_NOTE`、`DRIVER_RESULT` 便于复核。驱动的 notes
文件逐项列出成功判据的 0/1 结果。

边界：`--exit-timeout` 是**驱动等待工具退出的上限**，实机使用时必须覆盖
工具自身退出路径的停止与观测预算（`stop_timeout_ms` + 观测窗口 + 余量），
不能沿用离线测试的 0.3 s。`kill()` 只表示“驱动未能取得正常退出结果”，
**不表示设备已停止**，也不能替代独立停止措施。

## 4 离线反例结果

测试入口（不连接设备、不发送 UDP）：

```bash
cd AircraftPoseSystem/tools
python3 -W error::ResourceWarning tests/test_t2_acceptance_driver.py -v
```

三个 `.py` 平铺到同一目录也可运行（测试文件会回退到同目录导入）。
假子进程：`AircraftPoseSystem/tools/tests/fake_t2_tool.py`。
2026-10-22 实跑结果：**7 个用例全部通过（exit 0）**。

| 用例 | 假进程行为 | 期望 | 实际 |
|---|---|---|---|
| `normal`（正对照） | 两次到位、完整收尾、真实退出 0、日志 `EXIT_CODE 0` | 成功 | 通过 |
| `late_arrival` | P1 到位晚于 0.20 s 驱动超时 | 失败，`P1 timeout`，不误判成功 | 通过；迟到行留在日志但不计成功 |
| `real_exit_nonzero` | 两次到位、收尾行齐全、`normal_exit=1`、日志 `EXIT_CODE 0`，但真实进程退出码 3 | 因真实退出码失败 | 通过；仅 `exit_code_zero=0`，`exit_code_line_zero=1` |
| `log_exit_nonzero` | 两次到位、收尾行齐全、`normal_exit=1`、真实退出码 0，但日志 `EXIT_CODE 3` | 因日志退出码失败 | 通过；仅 `exit_code_line_zero=0`，`exit_code_zero=1` |
| `tail_output` | `quit` 后延迟 0.35 s 输出 `TAIL_AFTER_QUIT` 和收尾行 | 成功，尾部输出被收集 | 通过；日志含 `TAIL_AFTER_QUIT`、`FINAL`、`EXIT_CODE 0` |
| `exit_hang` | `quit` 后只输出 `EXIT_REQUEST`，不退出；测试用 0.3 s 退出上限 | 失败，超时强杀 | 通过；`forced_termination=1`、`timed_out=1` |
| `missing_final` | 两次到位、退出 0、有 `EXIT_CODE 0`，但无 `FINAL` | 失败 | 通过；判据 `final_normal_exit_1` 为 0 |

两个退出码反例互为鉴别：`real_exit_nonzero` 的日志收尾完全正常，只有检查
`proc.returncode` 才会失败；`log_exit_nonzero` 的真实退出码正常，只有检查
日志 `EXIT_CODE` 才会失败。因此不能再靠其中一个条件掩盖另一个缺陷。

变异检查（记录见仓库根 `验收证据/转台T2补验驱动_2026-10-22/04_变异检查.log`）：

| 变异 | 预期变红 | 实际 |
|---|---|---|
| `exit_code_zero` 强制为 `True`（移除真实退出码检查） | 仅 `real_exit_nonzero` | 7 个用例中仅该用例 FAIL，其余通过 |
| `exit_code_line_zero` 强制为 `True`（移除日志退出码检查） | 仅 `log_exit_nonzero` | 7 个用例中仅该用例 FAIL，其余通过 |
| 恢复原实现 | 全部通过 | 7/7 OK |

这说明两个退出码判据各自独立生效，不是靠另一个条件兜底。

上述结果只证明**驱动状态机**在假进程上的行为；不证明真实工具、真实
退出阶段或真实设备行为。收尾行齐全、EOF 与退出码 0 只能证明驱动**完整
收集了退出结果**；**“退出阶段零补帧”仍需逐帧核对**，`normal_exit=1`
本身不保证这一点。实机退出阶段若要取得该证据，仍需另行授权复跑；
本批不重发定位命令。
