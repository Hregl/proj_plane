## 0 这份文件怎么用

### 0.1 为什么需要裁决

本工程的一贯规则（README §6）：

> `2.md`~`11.md` 是**工作流文档**（逐阶段生成指令），`项目文档/` 下的 ENG/SYS 系列是**冻结设计文档**。
> 二者冲突时以冻结文档为准；两份冻结文档冲突时取**更具体**的一节。

这条规则能解决"文档打架"，但解决不了另一种情况：**冻结文档合起来仍然没有覆盖某个决定**，
或者**两条冻结条款同时生效会推出一个明显不该出现的结果**。这两种情况下本工程的处置一贯是：
不擅自发明，按"最保守的有界处置"实现，把缺口如实登记 —— 于是就有了这份清单。

### Q-A1 / Q-A2 粗姿态与舰体系变换的入参缺口（高）

**问题**：ENG-10 §2.3 Step 1 要求粗姿态来自"转台角度 + 距离估计"，但 SYS-04 冻结的
`solvePose` 入参只有 `CameraCalibration`（内含 `cameraToRig`），**既没有转台角度，
也没有 `rigToShip`**，而它却承诺产出 `ShipPoseResult.aircraftToShip`（舰体系结果）。

**现状**：`PosePipeline` 把整份 `OpticalRigCalibration` 作构造注入自行合成三级链；
转台角度/距离由 `setCoarseAttitude(az, el, distance)` 由应用层注入。

**影响**：算法层若要自己取转台角度就必须依赖设备层，违反 ENG-01 §17。目前用"调用方注入"
绕开，但**谁提供 `distance` 没有冻结依据**（见 Q-B 相关条目），M1 阶段的取值来自尺度估计，
实机上应来自何处无人回答。

**建议选项**：
1. 把标定与转台角度并入冻结入参（SYS-04 §7 修订）；
2. 或明文允许 `algorithm` 依赖 `optical`（并在 ENG-01 §17 改依赖图）。
**倾向**：选项 1。选项 2 会让"算法层可独立单测"这条既有能力受损。

### Q-A3 E 分项的 W 用检测框长边作上界代理（中）

选择阶段尚无匹配结果，W（结构点展布）用检测框长边代替。使 E 偏小、得分偏高（**乐观**），
但不改变候选间排序方向。**待定：接受该代理，还是把 E 从选择阶段移除。**

### Q-A4 `PoseValidationResult.confidence` 无算式（高）

ENG-09 §5.25 要求该字段、SYS-07 §12 只给"≥ `minConfidence`"与值域 [0,1]，
**从未定义算式**。现状取"重投影误差分项与内点比例分项的 **min**（最弱一环）"。

**影响**：两套实现各取各的 confidence 互不可比 —— 而它会进 result.json 与 SAVE 的判定。
**必须裁决**，否则该字段无法作为跨版本、跨实现的比较基准。

### Q-A5 `ValidationConfig` 无角分级判据（高，**阻塞验收**）· ✅ **已冻结 → C-001**

`ValidationConfig`（ENG-09 §6.6 冻结）只有 `maxReprojectionError`（**pixel**）、
`minInlierRatio`、`minConfidence`、`yawMin`/`yawMax`（**deg**，且是物理可达范围，
不是精度判据）。**没有任何以角分表达、或可折算为角分的误差容许字段**。

**后果**：验收指标"Yaw ≤ 1 角分"这个问句，在冻结类型里**无处可问**。1 角分目前只作为
`MeasurementSelector` 的 `E_ref`（评分参考）出现 —— 那是**评分**用的相对量，不是判定阈值。

**建议**：在 `ValidationConfig` 补 `yawMaxErrorArcmin`（含默认值）；
或明确"验收指标恒为 1 角分、不可配置、且只用于评分，判定不依赖它"。

### Q-A6 §2.5 冲突规则的 "2 pixel" 定义域（中）

ENG-10 §2.5 写"**反投影后**位置差 > 2 pixel 时以 B 类为准"，但"反投影"需要位姿，
而位姿要到 RANSAC 之后的 PnP 才存在 —— 与"选择/匹配都在 PnP 之前"（SYS-14 §17）
在时序上不能同时成立。现状落在**图像**距离上。**需要裁决明确该 2 pixel 的定义域。**

### Q-A7 机头朝向的 180° 二义性（中）

转台角度 + 距离无法区分迎头与尾追。现状**假定进近（迎头）**。若实为尾追，B 类定位失败 →
`cad_assisted = false` → 退回 A 类（丢精度但**不出错值**）。
**需要裁决**：是否引入"机头朝向"输入，或要求 A 类先判。

### Q-A8 / Q-A9 恢复预算的两处缺口（中）

- **Q-A8**：§7.3 + §7.4 + §7.6 约束 2/5 四条同时生效时，§7.4 的边预算恒被更早触发，
  §10 用例 3/4 期望的 **9002 实际不可达**。可到达 9002 的唯一路径是
  `CAPTURE → MEASURE_SELECT` 边。**需要裁决**：9002 应在何时可观测，或调整用例期望码。
- **Q-A9**：§7.4 的"三次排除"推导假定 VALIDATE 是唯一排除者，但 `MeasurementStrategy`
  在 MEASURE_SELECT 给不出候选时也会排除一台。两者不是同一种故障（"这台测不准" vs
  "这台连候选都给不出"）。**需要裁决**：后者是否计入回退预算。

### Q-A10 `TARGET_FOUND` 的三条规则叠加（高）

§5.3 无失败行、§7.7 无恢复行、§7.3 上限 1 —— 三条叠加的后果是：该状态一旦失败，
**既无经批准的恢复动作，也无重新进入的可能**。现状"就地 FAILED"。
**需要裁决**：§7.3 的"上限 1"是否只约束**状态内重试**，而不约束回退后的再次进入。

> 本轮实测再次确认该状态可达且会失败：`TARGET_FOUND -> FAILED`，用时 16 ms。

### Q-A11 008 之外是否新增操作控件（中）

9.md 的全部界面元素都是只读显示，而 ENG-04 §14 与 9.md §二 都把"用户操作"列为 UI 职责。
现状**不新增按钮**，相机切换 / AUTO-MANUAL 留待设计。
**需要裁决**：是否新增操作面板，以及哪些操作允许在 COMPLETE / FAILED 之外的状态下使用。

## 3 B 组：009/010 实测新发现

### Q-B2 `IRecorderSink::save(MeasurementTask)` 的信息量不足以产出结果包（**高**）· ✅ **已冻结 → C-002**

**问题**：SYS-04 §6.4 要求结果包包含 `cam25/50/100.raw`、`turntable.json`、`log.txt`、
`config_snapshot/`、`calibration_id.txt`、`result.json`。而 `IRecorderSink::save()` 的入参
是 `data::MeasurementTask`，它的全部字段只有三个：

```cpp
struct MeasurementTask {
    std::string taskId;
    ShipPoseResult result;
    PoseValidationResult validation;
};
```

**没有原图、没有转台角度、没有相机列表、没有时间戳、没有 `degraded`。**

**实测后果**：`Recorder::save()` 里被迫登记 `lastMissingFields_` =
`{camera_used, selected_camera, score, quality, feature_count, match_count}` —— 六项在
`MeasurementTask` 里**根本不存在**。`config_snapshot/` 与 `calibration_id.txt` 只能靠
Recorder 自己持有 `configDir` 旁路取得（已实现）。

**影响**：这是**当前唯一确定会让交付物不完整**的条目。相机原图是复现与责任认定的唯一凭据，
一旦漏掉无法事后补。

**建议选项**（三选一）：

>
> 配置目录本身的**默认值也是相对 CWD 的**：`src/app/main.cpp` 里 `configDir` 初值为
> `"config"`，只有 `argv[1]` 显式给了才换。所以"从哪个目录启动"决定的不只是日志去哪，

> | 工作目录 | 结果 |
> |---|---|
> | 安装根（`deploy/` 或 `build/install_check/`） | 事件循环起来（退出码 124） |
> | `bin/` 或 `build/` | **退出码 1**，打印"找不到配置文件" |
> | 任意目录 + `argv[1]` 指向配置目录 | 事件循环起来（124） |
>
> 第三行说明程序**并非只能从包根启动**——`argv[1]` 可以覆盖配置目录（README §2 已如实记载）。
> 但**只覆盖了配置**：`models/`、`calibration/`、`logs/`、`output/` 仍按 CWD 解析。
> 即"能用 `argv[1]` 启动"≠"路径问题解决了"，两者是不同的洞，别把一个当成另一个的补丁。
>
> 这条补充不改本条的裁决问题，只是把"影响面"从两个输出目录扩大到**四类输入/输出路径 +
> 配置解析基准**。`install_launch_check` 之所以必须显式设 `WORKING_DIRECTORY` 为安装前缀，
> 就是被这一条咬到的（见 `cmake/InstallRules.cmake` §6 的注释）。

## 4 本轮**已自行修复**、不需要裁决的缺陷

列出以供知悉。每条都有实测证据，且都是"不报错但结果错"这一类 —— 正是本工程反复标记
要防的类型。

### D-1 `PosePipeline` 的模型尺寸预检使注入阶段失效（2 处）

`estimateScale()` 与 `scaleEstimateOf()` 各有一份 `if (!(realSizeM > 0.0)) return false;`，
把可替换的 `scale_` 阶段与机型库硬绑。

- **对真实估计器是重复的**：`PinholeScaleEstimator::estimate` 自己第一件事就是同一条判断
  （`TargetScaleEstimator.cpp:57`，它必须自己判，因为 `realSizeM` 是它的入参）。
- **对桩是致命的**：M1 注入的 `MockTargetScaleEstimator` 永远不被调用。
- **实测症状极具误导性**：只修 `estimateScale` 一处时，`scaleEstimateOf` 把
  `out` **重置为默认值**，于是候选的 `targetPixelSize` 恒为 **0.0**，
  被 `min_target_pixel_size = 8.0` 全部淘汰 —— 报出的是
  "三路候选一个都不合格"，而三路的实测清晰度（222/240/270，门槛 1.0）
  与特征数（14，门槛 8）**都远超门槛**。失败原因指向门槛，真实原因是值被抹成了 0。

**修复**：两处预检都移除，判据归还给估计器（需要 L 的自己拒绝，不需要 L 的自己通过）。
**真实链行为逐位不变**：尺寸为 0 时 `PinholeScaleEstimator` 仍在同一点返回 false，
`out` 仍是默认值，调用方对 `confidence <= 0` 的冷启动先验路径一字未动 —— 变的只是"谁来做这个判断"。

**修复后**：状态机从 `TARGET_FOUND` 就地失败，推进到
`SEARCH → TARGET_FOUND → ALIGN → STABILIZE → MEASURE_SELECT → CAPTURE → POSE_SOLVE`。

### D-2 `MeasurementStrategy` 丢弃调用方报上来的失败原因

`TARGET_FOUND` 分支原先构造一个**全新的 `ErrorInfo`**，把 `deviceError.message`
整个丢掉。后果：现场只看到"TARGET_FOUND 无恢复路径"这句**规则说明**，
而真正的原因（"检测框退化"还是"尺度估计失败"）永远查不到 ——
一个是检出质量问题，另一个是机型库缺失，**处置方式完全不同**。

**修复**：保留原始 message 在前，规则说明在后，两句都要有。

### D-3 `Logger` 从不 flush，日志文件实测 0 字节

原先只写 `'\n'`，理由是"`endl` 强制 flush 会成为性能项"。该理由有两个漏洞，实测都发生了：

- **没有任何调用方会去 flush()**。现场最需要日志的时刻恰恰是进程非正常结束
  （崩溃、被 kill、被 timeout 终止），那时缓冲区里的内容永远丢掉。
  **实测：以 SIGTERM 结束进程后，`logs/aps_YYYYMMDD.log` 是 0 字节**，
  尽管程序已正常跑完整个启动流程并打印了 8 行 INFO。
- **省下的开销被高估**：flush 是一次 write（约 1~2 µs），而 INFO 级别是"每次状态迁移一行"。

**修复**：每行之后 flush stdout 与文件。**实测验证**：SIGTERM 后日志文件为 88 行、内容完整。

### D-4 `makeDirectories()` 在三份副本里都漏掉了路径分隔符

三份**逐字节相同**的 `makeDirectories()` 实现都少了分隔符，于是
`"output/measurement_x"` 会创建 `output` 与 `outputmeasurement_x` 两个目录 ——
**返回 true，没有任何报错**。

此前一直休眠，因为所有调用方都只用单级路径（`"logs"`、`"runtime"`）；
010 第一次走多级路径（结果包目录）才暴露：12 项断言全失败。

**修复**：合并为 `src/infrastructure/FileUtil.h` 的唯一实现，三份副本删除。

**这是配合 D-1 才生效的** —— 在 D-1 修复前，注入存在但从不被执行。

### D-6 `startMeasurement()` 的顺序缺陷：系统**再也开不出第二次测量**

`retry_.beginTask()` 必须排在 `transition(IDLE)` **之前**，原实现是反的。

- `stateMachine_.transition()` 对**目标状态**上报一次尝试（SYS-08 §7.6 约束 2）；
- `RetryManager::beginAttempt()` 第一件事就是查 `T_task`（§7.1 硬保证）；
- 若此时窗口仍是**上一次任务**的（`beginTask` 尚未调用），上一次的 deadline 一旦过去，
  `COMPLETE → IDLE` 这条**唯一入口**就被它自己的超时判据关死；
- 而 `beginTask()` 恰恰排在其后 —— 每次点击都在同一步返回，**计数永不重置**。

**实测症状极具误导性**：第二次启动的 `run()` 返回 **0 个 tick**，`notices` 里只有一条
"无法回到 IDLE：任务时限 T_task 已到，不再允许任何重试"，而 `state()` 仍是 `COMPLETE`
—— 看起来像"第二次测量**瞬间完成**"，而不是像"被拒绝"。

**为什么一直没被发现**：首次启动后**立刻**再点，上一次的 deadline 尚未到达，
`beginAttempt()` 放行，问题被完全掩盖；只有"隔了一会儿再点第二次"才发作。

**修复**：把 `retry_.beginTask(nowNs)` 提到 `transition(IDLE)` 之前
（代码内附完整推导）。**首次启动不受影响**。**实测验证**：修复前 `ticks2 = 0`；
修复后 `ticks2 = 11`、`saveCalls = 2`。

### D-7 `Recorder` 把非有限值写成 `nan`：**整份结果包事后读不出来，而 `save()` 返回 true**

`writeResultJson()` 用 `snprintf("%.6f", v)` 直接落盘浮点值。姿态非有限时写入 `nan`，
而 `nan` **不是合法 JSON** —— 事后用 `cv::FileStorage` 解析**整份文件失败**。

**为什么可达**：`PoseValidator::validate()` 的判据**对 NaN 是盲的**
（重投影 / 内点率 / 置信度 / 偏航四处比较遇 NaN 一律为假，于是不触发任何拒绝）。

**症状**：`save()` 返回 `true`（文件确实写成功了），但离线分析时**这份包完全读不出来**
—— 比"字段存在、数值看起来正常但语义不成立"更硬的一种。

**修复**（两层）：① `num()` 把非有限值一律写成 `0`
（**不写** `null` —— OpenCV 4.6 的 JSON 解析器不支持；**不写** `"nan"` 字符串 ——
`>> double` 会读成 `1.79e308`，比写 0 更糟，那是个"看起来合法"的数值）；
② 新增 `result.json` 的 `"non_finite_fields": [...]` 逐一点名，
与既有的 `missing_required_fields` 同一手法。正常任务下该表为空。

> ⚠ **`PoseValidator` 的 NaN 盲区本身没有修** —— "非有限姿态该由哪一层拒绝"是分层判断题，
> 见 §5 第 8 条（待裁决）。D-7 的修复是**兜底**，不是修复。

#### Q-C5 R07 修复后 E 分项的饱和区间（**登记项**）

R07 补回弧度→角分换算因子后，E 分项首次与冻结文档 §2.1 的表格同量纲。随之而来的
**可测量后果**（本轮新可见，此前因为低估 3437.75 倍而无从谈起）：

```
eNorm = 1 − min(1, E / E_ref)，E_ref = 1.0 角分（kYawErrorRefArcmin）
E = σ_px_est · √12 / (W · √N) × 3437.7468
```

- 默认回落值 `σ_px = 0.5`（`config/measurement.yaml: sigma_px_fallback`）、`N = 100` 时：
  **E = 595.4 / W 角分** ⇒ `W ≤ 595 px` 时 E ≥ E_ref ⇒ **eNorm ≡ 0**，E 分项不再区分候选；
- 标定后（σ ≈ 0.3）饱和点移到 `W ≤ 357 px` ⇒ **标定落地后区分区间反而变宽**。

饱和本身是 §3.6 的**本意**（"预测误差已达容许上限的候选不应被选中"），但对
**最小目标 / 退化展布**降低了区分度 —— 此时排序实际由其余三项决定。
既有用例 `SelectTakesMaximumAndKeepsPriorityOnTies` 仍通过，但**通过的原因变了**。
**落点**：`AlgorithmStageTest.MeasurementSelector.EFollowsEng10Formula`（§2.1 表格的
两组值 0.185109 / 0.925546 + `W=100` 的饱和断言）、
`MeasurementSelector.PredictedErrorIsArcminNotRadians`（量纲回归，
删掉换算因子即以 ≈3437.75 倍当场转红）。

> ⚠ **与本修复绑定的一句限定，不得省略**：本次修复**只重建了单位一致性**，
> 它**不证明整个误差模型已经通过实机标定** —— `σ_px = 0.5` 仍是回落值而非实测值，

> 这一条，不是"误差模型正确"这一条。

而降级失败"，推不出"不会因**其他**原因失败"。真实可达路径是 **ALIGN 对准命令越程**
（采集成功 → 检测偏差 → 计算转台命令 → `azimuth > azimuthMax` ⇒ 2002 ⇒ 同拍 FAILED）。
详见 README §6 第 92 行与 [V2.1-C01 §C-014](V2.1-C01_架构裁决变更说明.md) 的 v1.6 记录。
