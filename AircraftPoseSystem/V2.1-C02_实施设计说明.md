## 0 为什么先出设计而不是直接改

按评审裁定：这是**数据链问题**，拖到真实相机接入之后会连带影响 raw 保存、结果追溯与测试，
故优先级**高于**真实 SDK 接入；但先冻结设计再改代码。

写这份设计的过程中新发现两处缺陷，**其中一处比原登记的问题更严重**（见 §1.1、§1.3），
它们改变了本设计的性质：**这不是纯重构，而是行为修正**（见 §3）。

## 1 实测：这条链上有 5 处缺陷

### 1.1 ⚠ 新发现 D-C02-1：最佳帧**选了但没有用**（比原登记问题更严重）

| 位置 | 代码 | 事实 |
|---|---|---|
| `MeasurementController.cpp:735` | `pipeline_.selectBestFrame(capturedFrames_, bestIndex, quality)` | 评分**确实做了** |
| `:752` | `bestFrameIndex_ = bestIndex;` | 结果写入成员 |
| `:753` | `lastQuality_ = quality;` | 质量写入成员 |
| **`:790`** | `pipeline_.solvePose(lastFrame_, selectedCamera_, …)` | **PnP 用的是 `lastFrame_`** |
| `:711` | `lastFrame_ = frame;`（在 5 次循环**内**） | 故 `lastFrame_` = **最后一次**采集 |

**并且**：全仓库 `grep bestFrameIndex_` 只有 **两处**（`:201` 清零、`:752` 赋值），**无任何读取**；
`lastQuality()` 这个 public getter 也**没有任何调用者**。

**结论**：SYS-08 §5.7 冻结要求的"多帧采集……**选择**最佳帧"**实际上没有作用到结果上**。
本次 M1 的 PnP 输入是**第 5 帧**，而 `lastQuality_` 描述的是**评分最高的那一帧** ——
当两者不是同一帧时，**记录里的质量与被解算的图像对不上，且没有任何报错**。

这与此前 `PosePipeline` 的 `scale_` 那次是**同一类缺陷**：**算出来了，但没接到下游。**

### 1.2 D-C02-2：`capturedFrames_` 只留选定焦段一路（原登记项）

`:713-717`：

```cpp
const data::ImageFrame& image = frameOf(frame, selectedCamera_);
if (!image.image.empty()) { capturedFrames_.push_back(image); }
```

采 5 次三路齐的 `MultiCameraFrame`，只把 `selectedCamera_` 那一路存下来。
后果：结果包里**不可能**有另外两路的原图 —— 而 C-002 的交付物要求三路齐。

### 1.3 ⚠ 新发现 D-C02-3：空帧跳过破坏"索引 ↔ 采集序号"对应

紧接上一条的 `if (!image.image.empty())`：**只有非空帧被 push**，于是
"`capturedFrames_[k]` 就是第 k 次采集"这个隐含假设**不成立**。
若第 2 次采集的选定焦段为空，则 `capturedFrames_[2]` 实际是**第 3 次**采集。

**为什么这在本次设计中是致命的**：本设计的核心是"用评分选出的下标**回查**那一次采集"
（`bestFrame_ = capturedFrames_[bestIndex]`）。在错位的下标上回查，会取到**另一次采集的三路图**
—— 恰好就是 C-002 要修的那个缺陷（证据与结论不符），只是换了个位置复现。

故本设计**必须显式建索引映射**，不能依赖"位置相等"（见 §2.2）。

### 1.4 D-C02-4：成员注释与实现不符

`MeasurementController.h:363`：

```cpp
/// CAPTURE 阶段选出的最佳帧（供 POSE_SOLVE 使用）。
std::vector<data::ImageFrame> capturedFrames_;
```

该成员**既不是"选出的最佳帧"**（是 5 个候选）、**也没有"供 POSE_SOLVE 使用"**（PnP 用 `lastFrame_`）。
注释描述的是**意图**，实现不是那样 —— 这类注释比没有注释更危险：下一个人会照它推理。

### 1.5 D-C02-5：`selectedScore` 未留存

`stepMeasureSelect` 的 `data::MeasurementSelectionResult selection`（`:640`）是**局部变量**，
函数返回即丢弃。而 C-002 的 `MeasurementRecord.selectedScore` 需要它。
（已核实该结构确有 `score` 字段：`selectedCamera` + `score`，够用。）

## 2 修改清单（本设计要冻结的内容）

### 2.1 成员（`MeasurementController.h`）

```cpp
// ---- 改前（:348 :355 :363-364）----
data::MultiCameraFrame        lastFrame_;
data::ImageQuality            lastQuality_;
std::vector<data::ImageFrame> capturedFrames_;
int                           bestFrameIndex_ = -1;

// ---- 改后 ----
data::MultiCameraFrame              lastFrame_;       // 不变：SEARCH~STABILIZE 的实时帧
std::vector<data::MultiCameraFrame> capturedFrames_;  // 改：每次采集留**三路**
data::MultiCameraFrame              bestFrame_;       // 新增：产出该姿态的那一次采集（三路齐）
int                                 bestAcqIndex_ = -1;    // 改名，语义 = capturedFrames_ 的下标
data::ImageQuality                  bestQuality_;     // 改名：它是"最佳帧的质量"
data::MeasurementSelectionResult    selection_;       // 新增：留存 MEASURE_SELECT 的结论与评分
```

**改名理由**：`bestFrameIndex_` / `lastQuality_` 在本设计后语义变了
（前者从"视图下标"明确为"采集下标"，后者明确为"最佳帧质量"）。
**沿用旧名会让下一个人按旧语义读**——这正是 D-C02-4 的成因。

**改名成本已核实为 0**：`lastQuality()`（public getter）与 `bestFrameIndex_`
在 `src/`（除本文件）与 `tests/` 中**均无任何调用者**。

### 2.2 `selectBestFrame` 的处理：**不改算法层接口**（推荐方案）

`IPosePipeline::selectBestFrame(const std::vector<data::ImageFrame>&, int&, data::ImageQuality&)`
（`IPosePipeline.h:154`）**保持不变**。控制器侧：

```cpp
// ① 建"选定焦段"视图 + 采集下标映射（顺序严格一致；空帧只影响映射，不影响对应）
std::vector<data::ImageFrame> view;
std::vector<int>              viewToAcq;          // view[i] ← capturedFrames_[viewToAcq[i]]
view.reserve(capturedFrames_.size());
viewToAcq.reserve(capturedFrames_.size());
for (std::size_t i = 0; i < capturedFrames_.size(); ++i)
{
    const data::ImageFrame& img = frameOf(capturedFrames_[i], selectedCamera_);
    if (!img.image.empty())
    {
        view.push_back(img);
        viewToAcq.push_back(static_cast<int>(i));   // ← 唯一允许的换算，集中一处
    }
}

// ② 评分（算法层原样不动）
int viewBest = -1;
data::ImageQuality q;
if (!pipeline_.selectBestFrame(view, viewBest, q)) { /* 失败处置同现状 */ }

// ③ 映射回采集下标，并校核
if (viewBest < 0 || viewBest >= static_cast<int>(viewToAcq.size())) { /* 越界 → 失败 */ }
const int acq = viewToAcq[static_cast<std::size_t>(viewBest)];
bestFrame_    = capturedFrames_[static_cast<std::size_t>(acq)];
bestAcqIndex_ = acq;
bestQuality_  = q;
```

**为什么不改 `selectBestFrame` 的签名去吃 `MultiCameraFrame`**：那会把"按焦段取图"
这件**应用层**的事推进算法层，扩大算法层公开面（`IPosePipeline` 是 ENG-09 的接口清单成员），
且既有 `tests/algorithm/PipelineTest.cpp` 要跟着改。
本方案**算法层零改动、既有测试不破**，代价只是一个视图拷贝（`cv::Mat` 浅拷贝，代价可忽略）。

### 2.3 新的 CAPTURE → POSE_SOLVE 流程

```
captureFrameCount 次采集（每次一个三路 MultiCameraFrame）
        ↓  整帧留存（三路齐），不再只留一路
capturedFrames_ : N × MultiCameraFrame
        ↓  建"选定焦段"视图 + 索引映射（§2.2 步骤 ①）
view / viewToAcq
        ↓  selectBestFrame(view) → viewBest
        ↓  映射回采集下标（带校核）
bestFrame_ = capturedFrames_[viewToAcq[viewBest]]   ← 三路齐，且与评分同源
        ↓
stepPoseSolve: solvePose(bestFrame_, selectedCamera_, calibrationOf(selectedCamera_), pose)
```

### 2.4 重试路径：`switchToNextCamera` 的输入

`:774` 现为 `switchToNextCamera(lastFrame_)` → 改为 **`switchToNextCamera(bestFrame_)`**。

理由：换相机重算时输入应当是**同一次采集**（硬触发下三路同时曝光），
而 `lastFrame_` 是"最后一次采集"，与 `bestFrame_` 未必同一次。
该函数内部用 `pipeline_.selectCamera(frame, allowed, selection)`，接受 `MultiCameraFrame`，
`bestFrame_` 天然适配，**函数体不需改**。

> **A-1（需你确认）**：换相机后是否对**新焦段**重跑一次 `selectBestFrame`？
> **本设计推荐不重跑**，沿用同一采集下标：三路由触发同时曝光，`bestFrame_` 本身就是
> "同一瞬间的三路"，换相机换的是**通道**而不是**帧**；重跑会让"第 2 次必须换相机"
> 之外又多一个变量，反而不好归因。若将来评测显示同瞬间不同焦段的最佳帧差异显著，
> 再改为"按新焦段重选"，那是一次局部改动。

### 2.6 内存、生命周期与一处新增防御

- 量级：5 次 × 三路 × 5.0 MB（灰度 2448×2048）≈ **75 MB**。`cv::Mat` 浅拷贝，
  `capturedFrames_` 持有引用计数，SAVE 完成前不能释放（本设计正是要它活着）。
- **新增释放点**：SAVE 结束或任务终止后 `capturedFrames_.clear(); bestFrame_ = {};`。
  现状只在启动处（`:193` / `:200`）清空 → **任务之间会一直挂着 75 MB**，连续测量会累积。
- **新增防御**：`wanted` 现被 `min(max(captureFrameCount, 1), 100)` 夹住（`:699`），
  而 §5.7 的取值域是 **5~10**。100 帧 × 三路 ≈ **1.5 GB** —— 一个配置错误就能吃光内存
  （且 `cv::Mat` 分配失败的表现是抛异常或返回空 `Mat`，不是明确的配置错误）。
  **建议把上界收到 20**，并让夹取在日志中可见。
  > **A-2（需你确认）**：上界 100 → 20 是否同意。

## 5 测试计划：怎么造出"最佳帧 ≠ 最后一帧"

现状 `VirtualCameraBackend` 生成的图是**程序化**的（网格 + 目标块），5 帧图案相近，
评分很可能**单调或全等** → 判据 1 会"永远通过"。**必须先解决可测性。**

| 方案 | 做法 | 侵入性 |
|---|---|---|
| **1（推荐）** | 让 `VirtualCameraBackend` 对**某一帧**刻意降质（例如 `frameId == 2` 时降低对比度/加噪），使评分器自然把它排低，且**第 5 帧不是最佳** | 低：只改虚拟相机的图案生成，不改任何测试专用接口 |
| 2 | 给评分器加"按 frameId 设定分数"的测试预设 | 中：需新增测试专用选项（`MockPnPPoseEstimator::setPreset` 是先例） |

**推荐方案 1**，附加好处：它同时验证"评分器**真的在读图**"（若评分器不读图，
降质那一帧的分数不会下降，判据 1 立刻暴露）。

### 11.4 ⚠ D-C02-6 的 `frameId` 等式在**真实硬件**上未必成立

评审要求断言 `cam25.frameId == cam50.frameId == cam100.frameId`。在**虚拟相机**上成立
（三路共用同一个自增 `acquisitionId_`），但**真实硬件上有前提**：

- 每台相机的 `frameId` 是**该相机自己的帧计数器**。三台相机上电时间不同，
  计数器**起点不同** → 原始 `frameId` 天然不等；
- 只有在**硬触发**下、且做一次**首帧偏移锁定**（记录三路各自的基准 `frameId`，
  之后比较 `frameId - base`）之后，"同一次曝光"才等价于"偏移后相等"。

**风险**：若 011-A1 直接断言原始相等，它会**永远失败**，而届时最省事的"修法"是
**把这条断言放宽或删掉** —— 那正好等于亲手拆掉评审要加的安全网。

**建议**：把判据表述为"**三路曝光序号相等**"，在 `MultiCameraFrame` 内维护
`exposureIndex`（硬触发路径下由首帧锁定后的偏移量算出；虚拟路径下即 `acquisitionId_`），
断言 `exposureIndex` 相等；同时**在 011-A0 的适配层里就把基准锁定做掉**，
而不是留到测试里。这样断言在两种后端上都成立，且语义更强（它测的是"同一次曝光"，
不是"两台相机碰巧数到同一个数"）。

**此点在 011-A0 之前必须裁决** —— 它决定 `MultiCameraFrame` 是否要加第 5 个字段。

> ✅ **已裁决（2026-09-23）：原始 `frameId` 等式作为硬件验收条件被撤回**
> （评审判定"这个在真实系统错误"）。批准 `MultiCameraFrame` 新增
> `uint64_t exposureIndex;`，取值规则与 011-A0 的硬性前置见 **§12.2**。
> §10.2 那句"已在集成测试中断言三路 `frameId` 相等"**随之作废**，
> 改为断言三路 `exposureIndex` 相等。

### 12.2 `exposureIndex` 的取值规则（D-C02-6 的落地形态）

**语义**：三路图像的"这是第几次曝光"，从 1 开始计数。它替代了原先"三路原始
`frameId` 相等"的判据 —— 那个判据在真实硬件上**必然为假**（三台相机上电时刻不同，
各自的帧计数器起点天然不同），强行断言只会导致日后把断言放宽或删掉。

| 后端 | 取值 | 谁负责 |
|---|---|---|
| `VirtualCameraManager` | `exposureIndex = acquisitionId` | ✅ 本次已完成 |
| 真实相机（`ImvCameraBackend`） | `exposureIndex = frameId - baseFrame` | ⏳ **011-A0 必须完成**，且须早于 011-A1 |

**`baseFrame`（首帧偏移锁定）的规则**：三路各记录**第一帧**的原始 `frameId` 作为基准，

这一点是关键：降级不该让计数退化成"0 或重复值"，否则记录里的 `exposureIndex`

### 12.3 本次实施中发现并修复的**两个真实缺陷**

这两个都不是设计里的条目，是**新写的测试逼出来的**。

#### 12.3.1 `startMeasurement()` 的顺序缺陷：**系统再也开不出第二次测量**

`startMeasurement()` 里"`retry_.beginTask()`"与"回到 IDLE"的顺序原本是**反的**。

- `stateMachine_.transition()` 会对**目标状态**上报一次尝试（§7.6〔引用无效·依据待裁决·见 Q-D2〕 约束 2）；
- `RetryManager::beginAttempt()` 的第一件事是查 `T_task`（§7.1 硬保证）；
- 若此时窗口仍是**上一次任务**的，上一次的 deadline 一旦过去，
  `COMPLETE → IDLE` 这条**唯一入口**就被它自己的超时判据关死；
- 而 `beginTask()` 恰恰排在其后 —— 于是**每次点击都在同一步返回，计数永不重置**。

**实测表现**：第二次启动的 `run()` 返回 **0 个 tick**，`notices` 里只有一条
"无法回到 IDLE：任务时限 T_task 已到，不再允许任何重试"，而 `state()` 仍是 `COMPLETE` ——
**看起来像"第二次测量瞬间完成"**，而不是像"被拒绝"。

**为什么只在"隔了一会儿再点第二次"时发作**：首次启动后立刻再点，上一次的 deadline
尚未到达，`beginAttempt()` 放行，问题被掩盖。这正是它一直没被发现的原因。

**修法**：把 `retry_.beginTask(nowNs)` 提到 `transition(IDLE)` **之前**。
代码内已附完整推导（`MeasurementController.cpp`，`startMeasurement()` ①/② 两条注释）。
**首次启动不受影响**：`s == IDLE` 时本就要 `beginTask`；且 `reset()` 清的是**上一次**任务的计数，
而那一次此刻已经结束（函数开头已排除"任务进行中"）。

**证据（先红后绿）**：破坏后 —— `ticks2 = 0`，notices 出现"无法回到 IDLE：任务时限 T_task 已到"；
修复后 —— `ticks2 = 11`，`first = 11`，`second = 22`，`saveCalls = 2`。
该用例即 `MeasurementFlowTest` 的 `D_C02_6_连续两次测量的曝光序号单调递增`。

> ⚠ 附带说明：这条用例**表面上是为 D-C02-6 的曝光序号写的**，
> 实际拦住的是这个顺序缺陷 —— 它是"为了断言 A，结果照出了 B"。
> 断言 `ASSERT_GT(t2, 1)` 是**明确钉住本缺陷**的那一条。

#### 12.3.2 `Recorder` 把非有限值写进 JSON：**整份结果包事后读不出来，而 `save()` 返回 true**

`Recorder::writeResultJson()` 用 `snprintf("%.6f", v)` 直接落盘浮点值。当姿态非有限时
写入的是 `nan` —— 而 `nan` **不是合法 JSON**，`cv::FileStorage` 事后解析**整份文件失败**。

**为什么可达**：`PoseValidator::validate()` 的判据**对 NaN 是盲的**
（重投影 / 内点率 / 置信度 / 偏航四处比较遇到 NaN 一律为假，于是"不触发任何拒绝"），
于是非有限的姿态能一路走到落盘。

**危害形态**：`save()` 返回 `true`（文件确实写成功了），`sampling` 也正常，
但**离线分析时这份包完全读不出来** —— 与"字段存在、数值看起来正常但语义不成立"
是同一类，只是这次连读都读不到，属于更硬的一种。

**修法**（两层，缺一不可）：

1. `Recorder.cpp` 新增 `num()`：**非有限值一律写成 `0`**。
   - **不写 `null`**：OpenCV 4.6 的 JSON 解析器不支持 null（实测
     `Value 'null' is not supported by this parser`）；
   - **不写字符串 `"nan"`**：`>> double` 会把它读成 `1.79e308`（实测）—— 比写 0 **更糟**，
     因为 1.79e308 是个"看起来合法"的数值；
   - 代价是 `0` 也**不是**那个值，故必须配第 2 层。
2. 新增 `result.json` 的 `"non_finite_fields": [...]` 数组，逐一点名本次测量里
   **写成了 0 但它不是 0** 的字段（覆盖 `yaw / pitch / roll / reprojection_error`、
   全部 9 个旋转元素、3 个平移元素、validation 三项、score、quality 三项、
   statistics 两项、转台两项）。与既有的 `missing_required_fields` 同一手法。
   **正常任务下这张表为空**；非空即意味着本次测量的结果**不可直接使用**。

**实测证据**（真实落盘的一份包，NaN 偏航）：
`"yaw": 0` + `"non_finite_fields": ["yaw"]` + `"missing_required_fields": ["model_type"]`。

> ⚠ **仍未闭环**：`PoseValidator` 对 NaN 是盲的这件事**没有修**。
> "非有限的姿态该由哪一层拒绝"是**分层判断题**，需裁决（见 §12.5 第 5 条）。
> 本次只保证"即使漏到落盘，事后也读得出来、且看得见"。**这是兜底，不是修复。**
