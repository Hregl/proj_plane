### 0.7 分阶段通过判定汇总（2026-09-26 补）

**为什么要这一节**：第 1~10 项分属 A1／B／C 三个阶段，而**证据又分类别**（§1 表后说明；2026-09-28 起共**四类**，按**各自覆盖哪段路径**读，**不排强弱顺序**）。
不把"哪个阶段的通过由哪几项构成"写死，就会出现两种错法 ——
把 B／C 项当成 A1 通过的前提（A1 永远无法通过），或把 A1 的结论当成整条实机链路的结论（超出证据范围）。

| 阶段 | **通过的最小集**（缺一不得通过） | **阶段外项**（本阶段**不判、不勾**） | 判定边界 |
|---|---|---|---|
| **011-A1**<br>单相机接入 | 第 **1~6** 项各留证据，且每项须为**应用实际装配**类（§1 证据类别表）；其中第 4 项须记明 `Mono12` 的**实际格式／有效位深／打包／整帧总字节数**，第 5 项须为**实际生效**的模式且三项读回齐全；软件触发为 A1 的**必验**模式 | 第 7~10 项；**硬触发**（PH-01 待裁决，**不因"代码里有分支"而勾选**，§2.5）；`free_run`（真实后端返回 `NotImplemented`，本批不实施）；任何 2 路以上的结论；同步（§3.3） | 代码已实现／替身测试通过／无 SDK 构建通过**都不是**本阶段的实机证据（§6 的证据分类）；本阶段通过**不等于**"实机链路验收完成" |
| **011-B**<br>预览 / RAW / 安装启动 | 第 **7~9** 项；第 8 项须能**按帧自带字段**正确解码（§2.8）；第 9 项关闭 **H-10** | 第 10 项；硬触发；三相机构成 | 第 7~9 项可在 A1 未通过时**单独受阻**并如实记录（例如有设备但显示转换规则未定），二者互不顶替 |
| **011-C**<br>连续稳定运行 | 第 **10** 项（8 小时：丢帧、内存、错误情况） | 其余各项**已完成**是前提，但本阶段不再重复判 B／C 之外的新项 | 长跑通过**不能**反过来补 A1／B 的缺项 |
| **阶段外**（本清单**不**判） | —— | 三相机接入与同步；真实硬触发与自由运行；重连与完整恢复策略（Q-D1）；`Mono12Packed`；SDK 交付库的部署规则（011-B／R03） | 这些项的结论**不得**从本清单任一行推出（§6、§3.3） |

**三条配套纪律**（与 §0.1～§0.6 同源，此处只针对阶段判定）：

1. **"必验项全绿"才叫阶段通过**：任一项"部分通过"按 §0.4 记**未通过**，并写清卡在哪一步；
   不得用"其余都过了"折算。
2. **阶段外项不得出现在通过理由里**：例如"A1 通过，因为预览也看过一眼"——预览属 B，不补 A1。
3. **实机项与实现项的边界要分开写**：本批的实现与装配（含替身路径、两种构建）**可**记"已完成"，
   但**不得**混入上述阶段判定表当勾选依据（措辞见 §6）。

> ⚠ **按"覆盖哪段路径"读，不排"强弱顺序"**（2026-09-28 复核要求）：四类**覆盖面不同、互不蕴含**，
> 谁也替代不了谁。早先写作"后端直连**强度介于** SDK 探针与应用实际装配之间"的表述**已删除**。

> ∴ **SDK 探针通过不能替代后端集成验收**：探针成功只把问题空间缩小到"我们这一侧"，

## 2 逐项验收细则

### 2.1 USB 枚举（011-A1）

* **做什么**：接上相机，确认操作系统层可见。
* **必须记录**：接口类型（USB3 / U3V / 其它）—— 核验报告 §2 明确指出 `MU` 命名**不足以断言**为 USB3。
* **不得**：用"设备插上了"代替识别信息；用配置里的 `id: "cam25"` 代替实际枚举到的标识。

### 2.2 `IMV_EnumDevices`（011-A1）

* **判据**（两个判据**分开写**，不得合并成"型号序列号一致"）：
  * **型号**（`IMV_DeviceInfo.modelName`）须匹配目标机型 `A7A20MU201` —— 说明"是这样一台相机"；
  * **序列号**（`.serialNumber`）须匹配**设备标签上印的那一串**（即配置里 `serial` 的期望值）
    —— 说明"是**这一台**相机"。⚠ 三台同型号设备按型号或"第 0 个设备"打开，
    换线序后会**静默接错焦段**（`config/camera.yaml` 头部已写明这条理由）。
* **必须记录**：完整枚举输出（个数、**型号**、**序列号**、厂商、设备键、可用状态）。
* ⚠ **不得用配置里的 `serial` 当作枚举回报值**：配置是**期望值**，回报是**实测值**，
  两者在记录里必须是两栏（记不到回报就写"未取得"）。
* ⚠ **H-9 的实测点就在这里**：驱动不加载时，本项表现为"枚举 0 个设备"，
  与"代码写错"的症状相同 —— 必须先用 P-1 分离这两者，再把结论写进本项。

### 2.3 Open Camera（011-A1）

* **判据**：按**明确设备标识**（序列号，不是"第 0 个设备"）打开成功。
* **失败时**：必须留下**可定位的原因** —— SDK 返回的原始负数码 + 映射后的 ENG-09 §5.27 码。
  只写"打开失败"不合格（这正是 H-11 要解决的模糊）。

### 2.4 Mono12 采集（011-A1）

> ⚠ **本机型不提供 `Mono12`（2026-09-28 实机事实，批四）**：`IMV_SetEnumFeatureSymbol("PixelFormat", "Mono12")`
> 返回 **−111**（`/tmp/aps_imv_run.log` 15:05，启动即失败）。本台 `A7A20MU201` 可设置的只有
> **`Mono8` / `Mono10` / `Mono10Packed`**。故**本项在本机型上执行的是 `Mono10` 分支**：
> **2 字节/像素**（容器不打包）、**有效位深 10**（`IMV_GetIntFeatureValue` 读回 `validBits`；SDK 格式码
> `0x01100003`，即 `OCCUPY16BIT`）、**低位对齐**、**高 6 位补零**、满幅 **4096×3000** ⇒
> `IMV_FrameInfo::size == 24 576 000`。⚠ **预览用的显示右移量由此变**：Mono10 是 **`>> 2`**，**不是**
> Mono12 的 `>> 4`（见 §3.1）—— 若照抄 `>> 4`，画面会整体偏暗到几乎不可见，且**不会有任何报错**。
> ⚠ **后端请求的符号名本身已改为 `"Mono10"`**（`ImvCameraBackend.cpp` 的
> `kRequestedPixelFormatSymbol`，**不是**把用户请求的 `Mono12` 映射过去 —— 全仓没有映射逻辑，
> `camera.yaml` 也没有像素格式键，这一点不要写错），启动时会读回校验：
> **设备不接受即启动失败，不静默降级**。故本项记录里**"请求值"一栏写 `"Mono10"`**（即代码实际
> 发出的符号名），并注明本机型的可用集；**"实际格式"仍须以设备读回为准**，不得据请求值推断。
> ⚠ **本清单不据此勾选**：上面这条是**代码侧已实施**的事实，**不是**本项的实机证据 ——
> 本项要的是**设备读回的格式／位深／打包／尺寸／总字节数**。
> ⚠ **本节标题保留"Mono12 采集"**（历史编号与 §1 表沿用），但**判据按上表的通用项理解**：
> 记的是**设备实际格式 / 有效位深 / 打包方式 / 尺寸 / 整帧总字节数**，与具体叫什么名字无关。

* **必须记录**（**这一项是本清单最容易出错的一项**）：
  | 记什么 | 为什么 |
  |---|---|
  | 设备**实际**像素格式 | 不是请求的格式 —— 设备可能不接受请求值而回落到默认格式 |
  | **有效位深**与**打包方式** | Mono12 常见两种：**未打包**（2 字节/像素，16 位容器）与**打包**（1.5 字节/像素）。本批**只支持未打包**，打包形式（`Mono12Packed`）返回 `NotImplemented`。未打包时**有效位的位置**按 PFNC 2.4 §6.1.1 为**低位对齐、高 4 位补零**（SDK 的格式码 `0x01100005` 与 PFNC `Mono12` 逐位相符，见 §3.1） |
  | **整帧总字节数** `frameInfo.size`，以及 `width × height × 每像素字节` | 判据"长度与紧凑布局契约相容"的输入（见 §2.8）。⚠ **不记"步长"**：SDK 的 `IMV_FrameInfo` **没有** `step`/`stride` 字段（已逐字段核过，`IMVDefines.h:656-672`），其 `paddingX`/`paddingY` 的"行内 / 整帧"语义**未文档化**，**不得**用来推导步长 |
  | 尺寸（`width` / `height`） | 与 `config/camera.yaml` 的占位值 **1280×1024 大概率不同** |
* ⚠ **`config/camera.yaml` 的 `width` / `height` / `exposure_time` / `gain` 全部是虚拟阶段的占位值**，
  文件头已注明"Sprint 2 拿到真实相机后必须逐项替换为实测值"。
  本项记录的是**设备回报值**，**不是**该文件里的值。
* ⚠ **分辨率与标定的主点绑定**：换了分辨率而不换标定，主点会整体平移**而不报错**。
  本项若测得的分辨率与配置文件不同，必须同时登记"标定需重做"（属 014）。

### 2.5 Trigger 模式（011-A1）

* **必须记录**：请求值、**读回值**、以及两者是否一致。
* **软件触发与硬件触发分别记录**：
  * **本机无硬触发设备** ⇒ 硬触发项标 **"未执行／受阻"**，**不得**因为"代码里有这个分支"就勾选；
  * 硬触发的阶段归属本身受 **PH-01 待裁决**约束，不在本清单内定论；
  * ⚠ 硬触发**不是** 011-A1 的必验项（见 **§0.7 分阶段通过判定汇总**）：A1 的必验模式是**软件触发**。
    本批 `Hardware` **不实施**（PH-01）、`FreeRun` 对真实后端返回 `NotImplemented`，
    故这两个取值在本项**只能记"未执行／受阻"**，不得勾选、也不得阻塞 A1 的其余项。
* ⚠ **`trigger_mode` 已是三值字符串**（ENG-09 V2.3 起；旧版是 `1`=硬触发 / `0`=软触发）：
  `software` / `hardware` / `free_run`。**旧数字值被显式拒绝并给迁移提示**，不会静默映射 ——
  故实测时若看到"配置值非法"的启动失败，先核对配置是否还是旧数字形式，**不是**设备问题。
  本项须记录**实际生效**的模式，并说明与配置是否一致。
* ⚠ **读回必须读到三项**：`TriggerSelector`（应设 `"FrameStart"`）、`TriggerMode`（`"On"`/`"Off"`）、
  `TriggerSource`（`"Software"`/`"Line1"`）。**只读 `TriggerMode` 分不出软件触发与硬件触发**
  —— 两者都是 `"On"`，区别只在触发源。任一项读不到 ⇒ 如实记"未读到"，
  **不得**把"没读到"当作"模式正确"。

### 2.6 `ImageFrame` 填充（011-A1）

逐字段核对**来源**与**单位**，不得只看"有值"：

| 字段 | 冻结语义 | 本项要核的 |
|---|---|---|
| `frameId` | 采集端**单调递增**；仅用于诊断丢帧，**不用于同步** | 是否真单调；起点行为；溢出与重连后的行为 |
| `timestampNs` | **主机** `CLOCK_MONOTONIC`，`grab()` 返回后立即打点 | 是否取自单调时钟（**不得**是墙钟）；单位是 ns |
| `deviceTimestampNs` | SDK 上报的相机内部时间戳；**不可用时置 0** | 见 §3.2 |
| `cameraId` | **逻辑通道名**（`cam25`），与焦段角色绑定，**由配置决定**（`camera.yaml` 的 `id`）；⚠ **不是序列号**（ENG-09 §6.1，2026-09-26 更正） | 是否为配置里声明的逻辑名；**逻辑名 ↔ 硬件序列号是两栏**，绑定关系见下 |
| `role` | `CAM25` / `CAM50` / `CAM100` | 是否为 `CAM25` |
| `exposureTime` | 单位 **s**（不是 ms/µs） | 与设备读回值是否一致 |
| `image` | `cv::Mat`，**通道 1（灰度）或 3（BGR），深度 8U** | 见 §3.1 —— 这是本项与第 4 项**冲突的焦点** |

* **逻辑 `cameraId` 与硬件序列号的绑定关系**（2026-09-26 补 —— 这条语义在本批**改了**，
  故写进验收细则，不在验收表里"暗改契约"）：**逻辑名**来自配置（`camera.yaml` 的 `id`，
  如 `cam25`，与焦段角色绑定），**序列号**来自 SDK 枚举回报（设备标签上的那一串）。
  两者**不是一回事**，绑定靠 `camera.yaml` 里该通道的 `serial` 期望值：
  * 旧版曾写"`cameraId` 真实后端下即序列号"，那是**错的**：逻辑名一旦被当成序列号，
    `serial` 键就无处安放，换一台同型号相机要改 `id`（而 `id` 还被预览 / 落盘 / 界面引用）；
  * 本项要核的是"**这一路装出来的是不是配置里声明的那台设备**"——
    即 `config` 的 `serial` 与**设备回报的序列号**一致，而 `cameraId` 始终是配置里的逻辑名。
  改变该语义属**契约变更**，须走 ENG-09 §6.1 登记（已随 ENG-09 V2.3 完成），
  **不得**只在本验收表里改口径。
* **图像缓冲区有效性**：必须断言像素缓冲区可读、尺寸与 `step` 自洽
  （空帧、悬垂 `cv::Mat` 头、`step` 小于一行字节数，都是本项目已出现过的缺陷形态）。
  ⚠ 这里的 `step` 是 **`cv::Mat::step`**（**8U 显示图**的行字节数），**不是** SDK 的字段 ——
  `IMV_FrameInfo` **没有** `step`/`stride`（§2.4、§2.8 已记），原始载荷的长度只有 `sdkPayloadBytes`
  （＝`frameInfo.size`）一个权威来源。**不得**把两者写成同一件事。

### 2.7 Preview 显示（011-B）

* **判据**：真实画面**可见**，且**显示转换规则明确**（不得是"看起来能出图"）。
* ⚠ 详见 §3.1 —— 现有显示转换器**拒绝非 `CV_8U`**。

### 2.8 RAW 保存与读回（011-B）

* **判据**：保存的数据与**对应的那一帧**一致（不是"有文件生成"）。
* **必须验证**：保存的格式信息**足以正确解码**。⚠ 但"足以解码"的**依据要说准**
  （2026-09-26 更正）：
  * **总长度**的权威是 `frameInfo.size`（SDK 自报），元数据里记为 `sdk_payload_bytes`；
  * **布局**由**本批声明的紧凑契约 + 长度等式校验**判定 —— 即
    `sdk_payload_bytes == width × height × 每像素字节`，元数据里记为 `compact_size_matches`。
    ⚠ **该布尔量只能说明"长度与紧凑契约相容"，不是"布局已确认"**：
    相同的字节数对应多种像素排列是可能的。故元数据键名**不叫** `layout_confirmed` 之类；
  * **打包 / 有效位 / 字节序**按**项目定义**写明（`packing` / `valid_bits` /
    `valid_bit_alignment` / `declared_byte_order`），**不写成"SDK 保证"**；
  * ⚠ **`paddingX` / `paddingY` 未解释、不用于任何寻址或长度计算**（其"行内 / 整帧"语义
    未文档化，且 SDK 自身的 `Rotate`/`Flip` 与 `PixelConvert` 对 padding 的约定**不一致**）
    —— 元数据里作为**诊断信息**原样保留，**不写"行步长已确认"**（SDK 无 `step`/`stride` 字段）。
* ⚠ `cam*.raw` 是"**无头缓冲区 + 几何写进 `result.json`**"（C-02 §12.5 的既有裁决）——
  故**单独一个 `.raw` 不自证尺寸**，读回**必须**同时拿到元数据。本项须把这一依赖写成证据的一部分。
* ⚠ **进入落盘的帧一定是"已交付的成功帧"**：长度不符（`compact_size_matches == false`）
  的帧按契约**不发布**，故"长度不符的 RAW 进了结果包"这条路**不存在**。
  坏帧字节若要留存，属独立的诊断通道，不在本批。
* ⚠ **2026-09-28 批四的进展与边界**：本项的**第一条判据**（保存数据与对应帧一致、格式信息足以
  正确解码）已由**专项验证工具**实测通过（见 §2.11.4 的 **8a**）；但本项**不因此**覆盖
  "**应用正常测量流程自动触发 RAW 保存**"（§2.11.4 的 **8b**，**仍未验证／受阻**）。
  ⚠ 两者**互为独立判据**，**父项记 🟡 部分**（见 §1 表）。

### 3.1 Mono12 与预览的衔接（第 4 / 6 / 7 项的交叉点）

**现存事实**：显示转换器 `QtImageConverter::fromMat()` 在

```

     ├─→ RawImagePayload.bytes ：**原始载荷，逐字节等于 SDK 交付缓冲**
     │      （解码依据＝format / packing / validBits / declaredByteOrder；
     │        长度权威＝frameInfo.size；布局按本批声明的紧凑契约 + 长度等式校验）
     └─→ ImageFrame.image ：**8U 显示图**，`8U = 像素值 >> (validBits − 8)`
                               （不缩放、不直方图拉伸、不饱和；16 位按声明字节序组装）
```

> ⚠ **本机型代入公式的取值（2026-09-28 实机事实）**：`validBits = 10`（有效位深 10，2 字节容器），
> 故显示位移是 **`>> 2`**，**不是** `>> 4` —— `>> 4` 是 12 位的算法，在本机上会把画面压暗到几乎全黑
> **且不报错**。本机型的格式名是 **`Mono10`**（可设集只有 `Mono8`／`Mono10`／`Mono10Packed`，
> `"Mono12"` 返回 **−111**，见 §2.4）；本节标题里的"Mono12"是**历史名称**，判据按公式与字段走。
> ⚠ 本节的公式**不因机型而改**：`8U = 像素值 >> (validBits − 8)` 对 `Mono10`／`Mono12` 都成立，
> 变的只是代入的 `validBits`。

两条要点，本项验收时须逐条核对：

* **`image.type()` 只描述 8U 显示图**，**永远不作为原始载荷的解码依据** ——
  原始载荷怎么解只由 `raw` 的四个字段决定（上一版把两者混用过，已切断）；
* RAW 保真与显示转换**互不牵连**：RAW 的判据是"保存字节与 SDK 交付缓冲逐字节相同"，
  它靠**保留未经改动的原始副本**达成，与用哪种方式生成 8U 显示图无关。

**处理要求**：

1. **必须为显示生成一幅 8 位图像** —— 该转换是**显示路径专有**的，须有明确、可复查的规则
   （位深右移还是缩放、截断点在哪、是否允许饱和），并把规则写进运行记录。
2. **必须同时保留用于 RAW 的原始有效位深** —— 落盘的 `cam*.raw` 是**设备原始位深**的数据，
   不是显示用的 8 位图。
3. ⛔ **不得"整体降为 8 位"来掩盖问题** —— 那会让 Mono12 的 12 位动态范围在采集侧就丢掉，
   而 RAW、算法输入、误差预算全部**看起来正常**。这正是评审风险表里"真实图像格式 / 位深"★★★★★
   所指的情形，也与本项目反复出现的缺陷类（**字段存在、类型合法、数值看起来正常，但语义不成立**）同族。
4. 转换**发生在采集侧**（`ImvCameraBackend` 或其直接下游），**不得**在显示层加"输入位深开关" ——
   理由见 `QtImageConverter.cpp` 第 54~56 行的既有点评：那会让"同一个 `ImageFrame` 的通道顺序 /
   位深"不再唯一，所有下游都要跟着怀疑。
5. `pixel_format` 与后端**实际收到**的格式须做**一致性断言**：不一致**即失败**，**不是静默转换**
   （实施计划 §3.1 规则 4）。

### 3.2 时间戳（第 6 项的细则）

| | |
|---|---|
| **主机时间戳** | `timestampNs` 使用**约定的单调时钟** `CLOCK_MONOTONIC`，采集线程在 `grab()` 返回后立即打点。**不得**用墙钟（`CLOCK_REALTIME`）—— 离线部署下墙钟可能被 NTP 或人工校时跳变，一次校时就会让某帧的时差变成 ±数十秒，触发误判的丢帧告警 |
| **设备时间戳** | SDK **无设备时间戳时，`deviceTimestampNs = 0`** |
| ⛔ **禁止** | **不得把主机时间复制进 `deviceTimestampNs` 冒充设备时间。** 这会让"两路时钟偏移"这一类诊断数据**永远看起来完美**（偏移恒为 0），而真实的时钟偏移完全不可见 —— 属"注入了但没人读"的反面：**读了，但读的是假的** |
| 已有测试约束 | README §8.5 末已把两条写成必须存在的测试：VirtualCamera `timestampNs` **严格递增**；SDK 无设备时间戳时 `deviceTimestampNs = 0` 且 `deviceTimestampNs != timestampNs` |
| 单位 | 两者均为 **ns**（`uint64_t`） |

### 3.3 同步边界（必须写进任何一份运行记录）

> **单相机帧号及首帧锁定验证，不等于三相机同曝光验证。
> 相对帧号相等也不能单独证明物理同步。**

展开：

1. **本阶段只有一台相机**，故三路 `baseFrame` 锁定只能做**接口与逻辑验证**
   （虚拟后端 + 单元测试），**不能**做真机三路验证 —— 后者属 **012**。
   把"逻辑测过"写成"三路测过"是本条最常见的误用。
2. `exposureIndex`（`= frameId − baseFrame`，相对量）**相等**，证明的是
   "**两路各自数到的偏移相同**"；而它在"两路各自独立自由运行、恰好同速"时**同样成立**。
   ∴ 相对帧号相等**不能单独证明**物理同步。
3. **`Frame::synchronized` 字段的关闭**（README §8.5 第 5 条）只表示
   "**暂不增加该字段**"这个决定已定。`CameraSynchronizer` **至今仍未在运行的应用里被构造**，
   "**同步器未接入**"这一缺陷**仍然存在**。不得据该条的"✅ 关闭"推断同步已解决。
4. ∴ 本阶段产出的**任何帧号结论**，都**不得**表述为同步通过。出现"同步"字样时，
   必须同时写明适用的路数与触发方式。

## 4 元数据要求（须与"只有一台相机"的条件一致）

**当前真实接入通道的元数据，必须由真实设备与采集结果产生。** 逐条：

| # | 规则 |
|---|---|
| M-0 | **每个字段的"由谁生成"要说准**（2026-09-26 补）—— 它们**不是**一个来源：<br>· **型号 / 序列号 / 像素格式（含有效位深、打包、字节序声明）** ⇒ 来自 **SDK 回报**（枚举与设备信息、特性读回）；<br>· **主机时间戳**（`timestampNs`）⇒ 来自**主机单调时钟**，**不是**设备给的；设备给的进 `deviceTimestampNs`（可能为 0）；<br>· **角色（`CAM25/50/100`）与逻辑 `cameraId`** ⇒ 来自**配置 / 装配**，**不是**设备回报；⚠ **2026-09-28 批四起**：结果包里的 role **按"槽位"写出**（`Recorder::slotRole`），**不采信帧自报的 role**，且**有数据的帧**若 role 与槽位不一致 ⇒ **拒绝保存**（在任何 `.raw` 字节写出之前）；**合法无帧占位**（`data_source: "none"`）按槽位写 role、`frame_valid: false`、**不做该检查**（依据：ENG-09 V2.6 §5.6、SYS-04 V2.7 §15.3）；<br>· **落盘**：**采集层产出事实**（帧与元数据），**记录器负责把事实写进结果包** —— ⚠ **不要求后端去组装结果包**（后端不写 `result.json`、不决定文件名）。 |

| M-2 | **未接入通道不填造**序列号 / 尺寸 / 格式 / 时间戳。文件**可以不存在**；存在则须明确标注未连接 |
| M-3 | 若确实需要配置模板（供 012 三相机接入时用），**模板必须与采集证据分开存放**，并在文件内标注 `"status": "template"` 或等价的未连接标记。**不得**混入 `config/` 后与真实元数据无法区分 |
| M-4 | `pixel_format` 与后端实际收到的做**一致性断言**：不一致即失败 |

**三个归属问题**：

| 问题 | 答复 |
|---|---|
| **保存在哪里** | 随该通道的**采集输出目录**（与被描述的图像同级），**不是** `config/` —— `config/` 放的是**人对系统的配置**，元数据是**设备对采集的自述**，混放会让"配置错了"与"设备回报不同"无法区分 |
| **由谁生成** | **不是一个来源，按字段分**（2026-09-26 更正，同 M-0）：<br>· **型号／序列号／像素格式**（含有效位深、打包、字节序声明）⇒ **`ImvCameraBackend`**，它是唯一能看到 SDK 枚举与设备回报的一层；<br>· **主机时间戳**（`timestampNs`）⇒ **主机单调时钟**（不是设备给的；设备给的进 `deviceTimestampNs`）；<br>· **角色与逻辑 `cameraId` 绑定** ⇒ **配置／装配**（`camera.yaml` 的 `id` ＋ `SystemInitializer` 的按角色装配）；<br>· **落盘** ⇒ **采集层产出事实**（帧与 RAW 元数据），**`Recorder` 负责写进结果包**。<br>⚠ **不要求后端组装结果包**：后端不写 `result.json`、不决定文件名与目录 —— 那是记录器的职责（ENG-09／SYS-04 的分层）。<br>**UI 与 Application 不得参与填充**（对前三类都成立）。 |
| **RAW 读回用哪些字段** | **解码依据只有 `raw` 自身的字段**：`pixel_format` / `valid_bits` / `packing` / `declared_byte_order` **＋ 几何 `raw_image.width` / `raw_image.height`**（2026-09-26 定，2026-09-28 批四补几何）。⚠ `display_image` 的 `width`/`height`／`image.type()` **只描述 8U 显示图**，**不是**裸缓冲的解码依据，**且显示图可以为 0×0 而 RAW 仍然有效**（16:33 那次运行正是 `display_image` 0×0，见 §2.11.3）—— 故**不得**从显示图尺寸反推原始图几何。`raw_image` **仅在 `data_source == "raw"` 时写出**（回落路径没有原始载荷，写 0 会误导）。⚠ `width`/`height` 仍用于长度校验（`sdk_payload_bytes` 与 `expected_compact_bytes` 的比较），但不决定字节如何解释。 |

> ⚠ **H-2 仍然开放**：`cam*.json` 的 schema 是否要写进冻结文档（ENG-09 §6 只有 yaml 的键，未含 json）。
> 本节只定**当前阶段的取值规则**，**不**解决 schema 的冻结归属。
