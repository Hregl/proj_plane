# SYS-04 接口×代码一致性审计

**审计对象**：`项目文档/系统设计/SYS-04_接口控制文件ICD_V2.2_多相机闭环测量版.md`（1015 行）
**代码基线**：`AircraftPoseSystem/src/`（V2.1，2026-09-23 构建通过，10 套件 242 用例 0 失败）
**审计日期**：2026-09-24
**触发原因**：SYS-04 §15.1 声明 `IRecorderSink::lastErrorText()`，而代码中该方法不存在。为判断这是孤例还是同类偏差的冰山一角，对 SYS-04 声明的**全部**接口声明点逐个比对。

## 1 结论摘要

SYS-04 共 **21 个接口声明点**。逐条比对结果：

| 类别 | 数量 | 含义 | 处置方向 |
|---|---|---|---|
| ① 一致 | **7** | 声明与代码逐字段/逐方法吻合 | 不动 |
| ② 文档漏列 | **3** | 代码比文档更丰富，文档少写了 | **补文档**（纯文档动作） |
| ③ 文档领先于代码 | **7** | 文档声明了代码里**不存在**的类型或方法 | **需裁决**（见 §5） |
| ④ 签名形态差异 | **4** | 同名实体、不同签名形态 | **需裁决**（多为已登记偏离的漏同步） |

**一句话结论**：`lastErrorText()` 不是孤例。§15.1 只是 7 处「文档领先于代码」和 4 处「签名形态差异」中的一处；其中**最严重的一处不在 `IRecorderSink`，而在 §13.1**。

## 2 关键发现：IF-SW-02 / 「SYS-04 §4.2」是悬空引用

这是本次审计最重要的发现，且与接口清单本身无关。

**事实**：

1. **SYS-04 中不存在 §4.2。** §4 标题为「Data公共接口」，其下只有 `## 4.1 ImageFrame`，紧接着就是 `# 5 MultiCamera接口`。
2. **SYS-04 中不存在任何 `IF-SW-xx` 标识。** §3「接口分类」只列 8 个类别名（数据/设备/标定/坐标/算法/模型/记录/控制），无编号体系；§22~§25（依赖关系/禁止接口/版本管理/冻结总结）亦无。
3. **`IF-SW-02` 全 `项目文档/` 目录零命中。**
4. **但有 7 个文件把它当作冻结权威来引用**：

| 文件:行 | 引用原文 |
|---|---|
| [IPipelineObserver.h:9](src/algorithm/pipeline/IPipelineObserver.h#L9) | `SYS-04 §4.2（IF-SW-02：application ↔ algorithm 的唯一调用面）` |
| [PosePipeline.h:7](src/algorithm/pipeline/PosePipeline.h#L7) | `SYS-04 §4.2（IF-SW-02）` |
| [PosePipeline.h:179](src/algorithm/pipeline/PosePipeline.h#L179) | `它们**不属于 IF-SW-02**（SYS-04 §4.2 冻结的调用面只有…）` |
| [MeasurementFlowTest.cpp:486](tests/integration/MeasurementFlowTest.cpp#L486) | `SYS-04 §4.2 / IF-SW-02：**未检出返回 false**` |
| [ErrorInfo.h:114](src/data/ErrorInfo.h#L114) | `（IF-SW-02 冻结，不得改签名）` |
| [SystemInitializer.cpp:548](src/app/SystemInitializer.cpp#L548) | `（IF-SW-02 冻结）` |
| [README.md:357](README.md#L357)、[:382](README.md#L382)、[C-01:65](V2.1-C01_架构裁决变更说明.md#L65) | 同 |

**为什么这件事严重**：本项目近几轮裁决中，**「不属 IF-SW-02」被反复当作"可以动"的判据使用** —— 例如 C-008 同批删除 `PosePipeline` 的 6 个诊断访问器，其全部正当性来自 README §6 行 29 那句「它们**不属于 IF-SW-02**（SYS-04 §4.2 冻结的调用面只有 detect / estimateScale / selectCamera / selectBestFrame / solvePose / validate）」。**该判据的出处（SYS-04 §4.2）在冻结文档中不存在。**

这不是「文档写得不够清楚」，而是：**一条被用来批准代码改动的冻结依据，其文本不存在**。它恰好落在本项目长期追踪的缺陷形态里 —— 看起来有出处、引用格式完整、编号具体，而该编号指向空处。

**待裁决的关键问题**：那 6 个方法的冻结面**是由什么冻结的**？若 IF-SW-02 原文本已丢失，则需要**重建**该节并补齐编号体系，而不是把引用改成另一个也不存在的编号。

## 4 §13.1 是本次最严重的一处

`§13 PosePipeline接口 / §13.1 主接口` 声明：

```cpp
class PosePipeline
{
public:
    bool process(
        const MultiCameraFrame& frame,
        const CalibrationPackage& calibration,
        const TargetModel& model
    );
};
```

**三个独立问题**：

1. **`process` 在算法层零命中。** 真实调用面是 `IPosePipeline` 的 8 个纯虚。
2. **`CalibrationPackage` 与 `TargetModel` 作为入参类型，与 §9.1 / §10.1 的声明互相矛盾。** §13.1 假设"整份标定 + 整份模型"一次性传入；§9.1/§10.1 假设由 `ICalibrationManager` / `ITargetModelManager` 按角色查询。两种形态不能同时成立。而代码取的是**第三条路**：`PosePipeline` 构造期注入 `OpticalRigCalibration` + `TargetModelManager*`（见 README §6 行 38 的已登记偏离）。
3. **它与 §13.1 自己声称的权威冲突。** 按 README §6 行 29/35 的引用，`IPosePipeline` 的冻结调用面是 `detect / estimateScale / selectCamera / selectBestFrame / solvePose / validate` —— **这六个方法在 SYS-04 里任何地方都没有出现过**。§13.1 写的是 `process`。

也就是说：**SYS-04 §13.1 与 README 所引用的「SYS-04 §4.2」互相矛盾，而后者不存在。** 冻结 ICD 里关于算法层唯一调用面的文本，实际上只有那句无法编译的单方法 `process`。

§13.1 同节还声明输出为 `ShipPoseResult` / `MeasurementStatistics` / `PoseValidationResult` —— 其中 `MeasurementStatistics` 经**推送通道**（`IPipelineObserver::onStatistics`）输出，不是 `process` 的返回值，这是 C-02 裁决的结论；`ShipPoseResult` / `PoseValidationResult` 则确实是 `solvePose` / `validate` 的出参。**输出清单是对的，输入形态是错的。**

## 5 处置建议

按「文档同步修订，不改变现有软件架构」这一总约束，四类分别处置：

| 类别 | 项数 | 建议处置 | 是否属本批 |
|---|---|---|---|
| ① 一致 | 7 | 不动 | — |
| ② 文档漏列 | 3 | **改文档**：按代码实况补全 §5.1 / §16 / §18.1 | ✅ 本批可做，无争议 |
| ③ 文档领先于代码 | 7 | **改文档**：把 §9.1 / §10.1 / §11.1 / §13.1 / §15.1 / §4.1 / §21 改写为**代码实况形态**，并把"接口类尚未落地"作为**待实施项**登记（而非在 ICD 里当作已冻结事实） | ⚠ 需你确认方向 |
| ④ 签名形态差异 | 4 | **改文档**：§12.1 / §12.2 / §20.1 按代码实况改写；§12.3 已是登记在案的偏离，只需把 ICD 同步成偏离后的形态 | ⚠ 同上 |

**对 ③ 的方向，我的判断是「以代码为准、改文档」**，理由三条：

1. 你的约束是「**不改变现有软件架构，仅补齐遗漏、修正文档不一致、同步接口定义**」。若反过来以文档为准去补 3 个接口类和 ~7 个方法，那是新增架构，超出一项文档同步修订的范围。
2. 代码侧那些偏离**不是随意写的** —— `MeasurementSelector` 的 `bool` + 出参形态有 `MeasurementSelectionResult.h` 里成段的书面理由（哨兵值会经默认构造悄悄污染所有含该枚举的结构体）；`TargetModelManager::get(role)` 有 ENG-09 §5.20 / SYS-12 §8 的支撑（三个焦段各有独立特征库，无参 `getModel()` 表达不了"取哪一路"）。**这些是有依据的实现，不是欠债。**
3. 反向（以文档为准补代码）会立刻撞上 IF-SW-02 的悬空问题 —— 补出来的接口没有可引用的冻结依据。

**但 ③ 里有一条我建议单独处理**：`IRecorderSink::lastErrorText()`。它是你工作订单**明确要求** SYS-04 含有的（"`virtual std::string lastErrorText()=0;`"）。若按上面第 1 条删掉，就是删掉你亲自要求的内容。可选：
