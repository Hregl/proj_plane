**实测确认的 API 签名**（取自 `IMVApi.h`，供 011-A1 直接使用）：

```c

IMV_API int IMV_CALL IMV_EnumDevicesByUnicast(OUT IMV_DeviceList *pDeviceList, IN const char* pIpAddress);
```

⚠ **`IMV_EnumDevices` 的第二个参数是位掩码 `unsigned int`，不是 `IMV_ECameraType`**
（选错在 C++ 里会编译失败，但在 C 里会静默传错值）。实测常量（`IMVDefines.h:96-100`）：

| 常量 | 值 | 含义 |
|---|---|---|
| `interfaceTypeGige` | `0x00000001` | 网口 |
| `interfaceTypeUsb3` | `0x00000002` | USB3.0 |
| `interfaceTypeCL` | `0x00000004` | CameraLink |
| `interfaceTypePCIe` | `0x00000008` | PCIe |
| `interfaceTypeAll` | `0x00000000` | 全部（**CameraLink 除外**） |

⚠ **无实测证据**表明 A7A20MU201 属于哪一类（`MU` 命名**不足以断言**为 USB3）。
011-A1 应先用 `interfaceTypeAll` 枚举，再据 `IMV_DeviceInfo.nCameraType` 判定 ——
`nCameraType` 取值为 `typeGigeCamera=0 / typeU3vCamera=1 / typeCLCamera=2 /
typePCIeCamera=3 / typeUndefinedCamera=255`（`IMVDefines.h:108-115`）。

设备列表结构（`IMVDefines.h:540-544`）：

```c

} IMV_DeviceList;
```

⚠ `pDevInfo` 由 SDK 内部持有，**不要 free**。

### 3.1 三个必须处理的实测事实

**① 主库没有 SONAME，包内也没有 `libMVSDK.so` 软链。**
⇒ `find_library(NAMES MVSDK)` **永远匹配不到**（它只认 `libMVSDK.so` / `.a`）。
这正是评审第三节"不要 `find_library()` 盲搜"的实测依据。

**② 三个库的文件名与其 SONAME 不一致**（上表 ⚠ 行）。
⇒ 加载器按 **SONAME** 找，**不是**按文件名找。即便 `LD_LIBRARY_PATH` 指向正确目录，
也会在**打开相机时**才失败 —— 而不是启动时。故 `FindImvSdk.cmake` §4.3 主动补了
这三条软链（外加链接期需要的 `libMVSDK.so`）。

**③ `libMVSDK` 自身不依赖 Qt**（实测 `ldd` 无任何 `libQt*`）。
⇒ 排除包内 Qt 5.6.3 / 5.5.1 是**安全**的。GUI 才走 `libMVSDKGuiQt.so`。

### 3.2 依赖闭包实测

指向修正后的运行期目录时，`ldd` **`not found` 计数 = 0**：

```bash
LD_LIBRARY_PATH=<build>/imvsdk_runtime ldd third_party/imvsdk/lib/m64x86/libMVSDK.so.2.7.0.1.422704 \
  | grep -c 'not found'        # → 0
```

解析到的 SDK 内部库共 15 个（7 GenICam + 8 业务库），其余为系统库
（`libstdc++` / `libm` / `libgcc_s` / `libc` / `libdl` / `librt` / `libnsl` / `libgomp`）。

| 项 | 内容 |
|---|---|

| 链接 | `-L<runtime>;-lMVSDK` |
| 构建树 RPATH | `-Wl,--disable-new-dtags -Wl,-rpath,<runtime>`（**本次新增**，见 §6.4） |

### 6.3 ✅ 端到端实测：经**真实接口**链接并运行成功

**这是本报告的核心证据。** 探针**实际调用** `IMV_GetVersion()` 与
`IMV_EnumDevices()`（不是空壳），并**直接 `include` 工程的真实 `Dependencies.cmake`**
（不是手抄一份等价参数 —— 手抄的等价物证明不了接口本身是对的）：

```cmake
include("<工程>/cmake/Dependencies.cmake")
add_executable(imvprobe imvprobe.cpp)
target_link_libraries(imvprobe PRIVATE aps::imvsdk)
```

实测结果：

```
$ ./build/imvprobe              # 未设任何环境变量
[1790172575.462139] [interface.c:812:getDriverVersion] Unload Universal Ethernet drivers.
IMV_GetVersion() = 2.7.0.1.422704
IMV_EnumDevices(All) ret=0 (IMV_OK=0), 发现设备数=0
退出码 0

$ readelf -d ./build/imvprobe | grep -i "needed.*MVSDK\|rpath"

```

**三条结论**：

1. **DT_NEEDED 里是文件名 `libMVSDK.so`，不是绝对路径** —— 证实主库无 SONAME 时
   `-l` 的写入行为，二进制**可重定位**（构建树搬走不会带死路径）。
2. **`libMVSDK.so` 由主库自己的依赖闭包（GenICam 等）能全部解析** —— 证明 §3.1②
   的三条 SONAME 修正软链是**必要且有效**的。
3. **零环境变量下运行成功** —— 证明 `aps::imvsdk` 这个接口本身是完整的，
   011-A1 直接 `target_link_libraries(... aps::imvsdk)` 即可，不需要额外手工配置。

### 6.4 ⚠ 本次修复：RUNPATH 不传递（原设计**跑不起来**）

**实测发现**：只给 `-L<runtime> -lMVSDK` 时，二进制**链接通过、启动即失败**：

```
$ ./imvprobe
./imvprobe: error while loading shared libraries:
    libGCBase_gcc421_v3_0.so: cannot open shared object file: No such file or directory
退出码 127
```

**根因**：现代 binutils 默认 `--enable-new-dtags`，`-Wl,-rpath` 生成的是
**RUNPATH**；而 **RUNPATH 不传递** —— 只作用于可执行文件**直接**链接的库，
不作用于那些库**自己再加载**的依赖。于是"可执行文件找得到 `libMVSDK.so`，
而 `libMVSDK.so` 找不到 `libGCBase…`"。

**实测的两种修法**（均验证通过，取其一即可）：

| 修法 | 结果 | 代价 |
|---|---|---|
| `LD_LIBRARY_PATH=<runtime>` | ✅ 运行成功 | 每个运行入口都要记得设 |
| `-Wl,--disable-new-dtags` → **DT_RPATH**（可传递） | ✅ 运行成功 | 无 |

**采用后者**，加在 `aps::imvsdk` 的 `INTERFACE` 链接选项上，用 `$<BUILD_INTERFACE:…>`
限定作用范围（安装后的 `deploy/` 不继承，符合 `CompilerOptions.cmake` §4 的
`CMAKE_SKIP_INSTALL_RPATH ON`）。

**这是本项目一贯警惕的失效形态的又一实例**：配置成功、构建通过、无任何告警，
**运行才失败**。若非用真实调用 SDK 符号的探针去跑，这个问题会一直潜伏到
现场接上相机的那一刻。

### 6.5 ⚠ 一处已修复的长期失效：`CMAKE_MODULE_PATH` 从未设置

**实测发现**：`find_package(<Pkg>)` 的 MODULE 模式**只**查 `CMAKE_MODULE_PATH`
与 CMake 自带 Modules 目录，**不含**调用者所在目录。本工程原先从未设置该变量
（`--debug-find-pkg=ImvSdk` 显示只搜索了 `/usr/share/cmake-3.31/Modules/`）。

⇒ `cmake/FindImvSdk.cmake` 与 `cmake/FindTurntableSdk.cmake`
**从写下来那天起就没有被加载过一次**，`-DIMV_SDK_ROOT=<真实路径>` 也不可能生效。

**已修**：`cmake/Dependencies.cmake` §0 增加
`list(APPEND CMAKE_MODULE_PATH "${CMAKE_CURRENT_LIST_DIR}")`。

⚠ **这个失效长期未被发现的原因值得记录**：它的表现与"预期状态"完全一致 ——
打印的是"未找到 ImvSdk（非致命）… 拿到 SDK 后：cmake … -DIMV_SDK_ROOT=…"，
而"Sprint 2 之前本来就没装 SDK"正是当时的真实情况。**失败信息看不出是
"没装"还是"查找器压根没跑"** —— 与本项目反复出现的
"断言没验它自称要验的东西"属同一族缺陷。

**配套修复**：`FAIL_MESSAGE` 原先是一个含 `;` 的未加引号多行参数，CMake 会按
列表切分，导致 `CMake Error at FindPackageHandleStandardArgs.cmake:414`、
配置中断。已改为先赋给单一带引号变量再传入。

## 7 已知缺口与开放项

### 7.1 ⚠ 内核 6.6.0 超出厂商声明上限（未闭环，最高风险）

| 来源 | 允许的内核上限 |
|---|---|
| 手册 §1.2 | 6.2.0 |
| 包内 `bin/common/install.sh` 的版本检查 | **5.0.0** |
| **本机实际** | **6.6.0-amd64-desktop** |

**三条均超出。** 影响面：**U3V/GigE 相机依赖内核驱动模块**（`module/m64x86/`），
若驱动在 6.6.0 上不能加载，则"枚举到设备"这一步就会失败 —— 与我们的 C++ 代码无关。

**本报告不能判定**其可用性（**本机无相机，无法实测**）。
**011-A1 的第一步**应当是：接上 A7A20MU201，跑 `IMV_EnumDevices`，
**看能否枚举到设备**。这一步同时验证了内核兼容性 —— 它必须先于任何代码改动。

**若枚举失败**，可选退路（按优先级）：
1. 让厂商确认 6.6.0 支持，或提供更新的驱动；
2. 在允许的机器上接入（但这与"三相机 25/50/100 mm 全链"部署目标冲突，需评审）；
3. 评估纯用户态 USB3 路线是否可行（**当前无证据**，不作为方案提交）。

### 7.2 ⚠ 安装后（deploy/）无法定位 SDK 库 —— 无任何机制

`CompilerOptions.cmake` §4 设 `CMAKE_SKIP_INSTALL_RPATH ON`（正确：`deploy/bin`
不得指向开发机构建目录），`InstallRules.cmake` §4 会把 runtime 目录装到
`deploy/lib`（正确）。**但两者之间没有桥**：没有任何地方为 `deploy/bin` 里的
可执行文件设置 `LD_LIBRARY_PATH`，也没有启动脚本、没有 `/etc/ld.so.conf.d` 条目。

⇒ **现场解压后直接运行 `deploy/bin/AircraftPoseSystem` 会因找不到 `libMVSDK.so`
而启动失败**（与 §6.4 同源，但发生在安装态、且 §6.4 的修法被 `BUILD_INTERFACE`
刻意排除在外）。

**本次不修**：这属于"程序怎么启动"的范畴，是 **011-B**（真实 Camera→Preview→Recorder
全链）的交付内容，且修法可能涉及启动脚本 / 环境变量 / RPATH 三选一的设计决定。
**登记为 011-B 的必办项**，不得遗漏 —— 它会精确地在"交付到现场"那一刻爆发。

### 7.3 ⚠ SDK 错误码是负数，不能直接当 ENG-09 §5.27 的码返回

`IMVDefines.h` 的错误码为 **负值**（`IMV_OK = 0`，失败为 `-100` 段等），而
ENG-09 §5.27 的相机段是 **1000~1999 的正数**，且 `code == 0` 语义是"未设置"。

⇒ **011-A1 必须做显式映射**，不得 `return ret;` 透传。否则：
- 负数码会让 `errorCodeName()` 落到 `default:` → `"UNREGISTERED"`；
- 更糟的是 **`IMV_OK == 0` 与"未设置"同值** —— 若不映射，一次成功的调用
  返回的 `0` 会被下游当成"没有错误信息"或"失败"，语义直接错位。

**011-A1 需新增**：相机段内区分"SDK 调用失败（-XXX）"与"设备未找到"的具名常量，
并在日志中**保留原始负数码**（它是对厂商追责与查手册的唯一线索），
同时对外给出 ENG-09 段码。

### 7.4 运行期前提（软硬件环境，非代码）

| 项 | 要求 | 依据 / 状态 |
|---|---|---|
| **`usbfs_memory_mb`** | `echo 1000 > /sys/module/usbcore/parameters/usbfs_memory_mb`（**需 root**） | 包内 `bin/common/set_usb_stack.sh`。⚠ 若 A7A20MU201 为 U3V，不设会导致缓冲不足/丢帧；**接口类型待 011-A1 实测**（§2） |

## 8 对 011-A1 的约束（可直接照做的清单）

1. **链接**：`target_link_libraries(<target> PRIVATE aps::imvsdk)` 即可。
   头文件路径、库路径、runtime RPATH 都由该接口传递（§6.3 实测）。
   **不要**自己写 `-I` / `-L` / `-l`。
2. **头文件**：只 `#include "IMVApi.h"`。不要引入 `IMVFG*`（§2）。
3. **枚举**：第二参数用 `interfaceTypeAll`（`0`），据 `nCameraType` 判定接口类型；
   `pDevInfo` 由 SDK 持有，**不要 free**（§2）。
4. **错误码**：必做显式映射，保留原始负数码入日志（§7.3）。
5. **第一步不是写代码**：先接相机跑 `IMV_EnumDevices`，确认内核 6.6.0 下能枚举到
   设备（§7.1）。**这一步失败则后续全部无意义**，且与 C++ 代码无关。
6. **框架可编译性不得破坏**：`APS_HAVE_IMVSDK` 分支保持
   `#ifdef 真实实现 / #else 诚实桩 / #endif` 形态（评审第四节）。
   当前桩用 `#pragma message` 报告"SDK 在但适配未写"，**不要**用 `#warning`
   （`ENABLE_WERROR` 会把它变成错误，重新引入阻断编译的问题）。
7. **不改** `IPosePipeline`、不改算法接口 —— 设备层照 `ICameraBackend` 契约实现。

## 9 核验的可复现命令

```bash
B=AircraftPoseSystem/third_party/imvsdk
R=<build>/imvsdk_runtime

# ① 包完整性（Makeself 自带，不是整文件 md5sum —— 见 README §1.2）
sh MVviewer_Ver2.7.0.1_Linux_x86_Build20260709.run --check

# ② 架构
file -b $B/lib/m64x86/*.so | sort -u

# ③ SONAME（判 §3.1② 的三处不一致）
for f in $B/lib/m64x86/*.so*; do printf "%-38s %s\n" "$(basename $f)" \
  "$(readelf -d $f 2>/dev/null | grep SONAME | sed 's/.*\[\(.*\)\]/\1/')"; done

# ④ 依赖闭包（应为 0）
LD_LIBRARY_PATH=$R ldd $B/lib/m64x86/libMVSDK.so.2.7.0.1.422704 | grep -c 'not found'

# ⑤ 端到端（需一个真实调用 IMV_* 的探针；空壳探针会被 --as-needed 优化掉，
#    得到"无 DT_NEEDED"的假阴性 —— 本报告 §6.3 的探针调用 IMV_GetVersion）
readelf -d ./imvprobe | grep -i "needed.*MVSDK\|rpath"
./imvprobe
```

⚠ **⑤ 的陷阱值得单列**：若探针只链接而不调用任何 `IMV_*` 符号，链接器
（`--as-needed`，现代发行版默认）会把 `libMVSDK` 整个丢掉，`readelf -d` 得到
**空结果**。这会被误读为"链接失败"。**必须先真实调用至少一个 SDK 符号**，
测量才有意义 —— 本报告第一版就踩过这个坑。
