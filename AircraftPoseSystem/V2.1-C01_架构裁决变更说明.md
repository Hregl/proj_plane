## C-001 补充验收精度判据

**对应缺口**：Q-A5 · **严重程度 ★★★★★** · **第一批（必须）** · **状态：通过（评审维持原方案）**

### 裁决结论

1. `ValidationConfig` 新增 `yawMaxErrorArcmin`，取值 **1.0**，由 `measurement.yaml`
   提供（键名 `yaw_max_error_arcmin`）。
2. **1 角分从"评分参考"升级为"可配置的验收阈值"**，但——
3. `PoseValidationResult` **不新增** `yawErrorArcmin` / `accuracyQualified`。

第 3 条与最初提议不同，理由是**本条的要害**，见下。评审已确认此修正正确。

### ⚠ 为什么不能把 `yawErrorArcmin` 放进 `PoseValidationResult`

**Yaw 误差需要真值，而现场没有真值。**

`yawError = |实测 yaw − 真实 yaw|`。真实 yaw 只能来自转台上的已知角度、
外部更高精度基准（经纬仪等）或其它独立测量手段。

**在舰载现场测量一架真实飞机时，这三个都不存在** —— 系统本身就是要给出那个角度。因此：

| 若照原提议实现 | 后果 |
|---|---|
| `PoseValidationResult.yawErrorArcmin` | 现场**只能填 0 或 NaN**。填 0 表示"零误差"（谎报），填 NaN 会污染 `result.json` 的数值字段 |
| `PoseValidationResult.accuracyQualified` | 现场**恒为 false**。若 SAVE 的通过判定读它，则**每一次现场测量都会失败** —— 一个"永远测不出结果"的系统，而根因是判据本身不可判 |

这正是本工程反复防的那类缺陷：**字段存在、类型合法、数值看起来正常，但语义不成立**。

### 落地方式（评审已定：两阶段）

**把"自洽性判定"与"精度判定"分开**：

| 层 | 判定 | 有无真值 | 去处 |
|---|---|---|---|
| 自洽性（现状，不变） | 重投影误差、内点比例、confidence | 不需要 | `PoseValidationResult.valid`（现状） |
| **精度（新增）** | `yawErrorArcmin ≤ yawMaxErrorArcmin` | **需要** | **离线验收层** `AccuracyReport`，真值显式注入 |

```
config/measurement.yaml
  yaw_max_error_arcmin: 1.0        # 新增；0 或缺失 = 不做精度判定

src/data/ValidationConfig.h        # 新增字段（ENG-09 §6.6 变更）
  double yawMaxErrorArcmin = 0.0;  # 0 = 未配置，与既有字段的哨兵约定一致

离线验收层（新增，不动 PoseValidationResult）
  输入：本次 task + reference_yaw（可空）
  输出：yawErrorArcmin / accuracyQualified / referenceYawSource
```

**真值的两阶段约定（O-1 的结论）**：

| 阶段 | `reference_yaw` | 行为 |
|---|---|---|
| **软件阶段**（现在） | `null`（缺省） | **不判定**。报告中写 `"accuracy": "not_evaluated"`，**绝不写 `qualified: true`** |
| **实验验收阶段** | 例如 `35.000`（度） | 计算 `yaw_error_arcmin`，与阈值比较，标注真值来源 |

**⚠ 真值来源不绑定转台。** 理由：最终舰载环境下的**转台角度 ≠ 飞机真实姿态**
（转台是对准工装，飞机有其自身的纵轴与停放姿态）。因此 `AccuracyReport` 只接受
一个**载体无关的 `reference_yaw` 数值 + 来源标签**（`turntable` / `theodolite` /
`offline_compare` / `null`），由测试工装或离线工具填入。这样做的收益是：
将来真值来源换成任何一种，验收层都不用改。

### 已关闭的开放点

- **O-1 → 已定**：两阶段（上表）。软件阶段不做精度判定，不阻塞 011。
- **O-2 → 已定**：阈值沿用 `measurement.yaml`（`max_reprojection_error` 等已在那里）。

### 验收标准

- 配置里改 `yaw_max_error_arcmin` 能被读到并在启动日志中体现；
- `reference_yaw` 为空时，结果包**不出现** `accuracy_qualified: true`，而是 `not_evaluated`；
- 有真值的测试工况下，`yawErrorArcmin` 与人工计算一致（相对误差 < 1e-6）。

### ⚠ 实施前置：现在拿不到"用于解算的那一次采集"

实测（`MeasurementController`）：

```cpp
std::vector<data::ImageFrame> capturedFrames_;   // :363 —— **只有 selectedCamera_** 的 5 帧
data::MultiCameraFrame        lastFrame_;        // :348 —— **最后一次**采集（三路齐）
```

- `stepCapture()` 采 5 次，每次得到一个三路 `MultiCameraFrame`；
- 但只把 **selectedCamera_ 那一路**存进 `capturedFrames_`（`MeasurementController.cpp:713-717`）；
- `lastFrame_` 存的是**最后一次**采集，而解算用的是 `selectBestFrame()` 选出的**最佳帧**。

**后果**：若把 `lastFrame_` 塞进 `MeasurementRecord`，结果包里的
`cam25/50/100.raw` 会是**另一次采集**的图像，而不是产出该姿态的那一次。
**证据与结论不符，且不会有任何报错** —— 事后追溯时"图像看着正常、姿态也正常，
但两者不是同一次曝光"。

**因此 C-002 的实施前置**：`stepCapture()` 必须把**最佳帧所在的整个
`MultiCameraFrame`**（三路）留存下来。实现上建议 `capturedFrames_` 的元素类型由
`ImageFrame` 改为 `MultiCameraFrame`（`selectBestFrame()` 的入参需同步调整，
它只用选定焦段，语义不变）。

**内存量级**：灰度 8 位 2448×2048 ≈ 5.0 MB/路，三路 ≈ 15 MB/次采集；5 次 ≈ 75 MB。
`cv::Mat` 是引用计数浅拷贝，故"按值放进 `MeasurementRecord`"不复制像素，
但会**延长这些缓冲区的生命周期**到 SAVE 完成。**O-5 → 已定：只留最佳帧**
（不留 5 帧全部）——理由是 5 帧的价值可由日志中的 quality 序列替代，
而 75 MB 级常驻不值得。存进记录的那一份在 SAVE 后随记录析构释放。

## C-005 亚像素定位（技术风险最高项）

**对应缺口**：README §6 第 57 行 · **严重程度 ★★★★★** · **第二批（011 后实施，但需现在修订文档）**
**状态：通过（评审完全同意修正）**

### 裁决结论

1. 确认该缺口为**精度体系的头号风险**：SYS-15 §4 的合成结果是 **0.97 角分**，
   指标 1.0 角分，**余量仅 3%** —— 而这个余量建立在一个**实现尚未达到**的
   亚像素定位精度假设上。
2. `CadStructureLocator` 增加亚像素细化步骤。
3. **SYS-12 / SYS-15 需修订**：把"预期 0.1~0.2 pixel"从**期望**改为**要求**，
   并明确未达到时误差预算的后果。
4. **不立即选方案**：先做 C-005 实验任务（见下），用数据决定（评审已定）。

### ⚠ 一处需要更正：缺陷不在 SIFT，在 CAD 结构点

原提议提到"不要 SIFT keypoint 整数化"——**SIFT 不是问题所在**。
OpenCV `SIFT` 输出的 `KeyPoint.pt` 本身就是浮点，且其内部对极值做了二次拟合。

**实测确认的问题在 CAD 路径**（README 第 57 行原文）：

> 本实现对 `cv::Canny` 的**整数**边缘图做直线拟合，与像素栅格对齐的边缘
> 因此无法取得亚像素位置……实测残差 0.000、四点离散 0.000，
> 即**重复性**很好但**绝对精度**受量化限制。

即：`CadStructureLocator` 在整数边缘上拟合直线、求交点，
故与栅格对齐的棱边只能落在整数坐标（实测在 199/200 间跳变）。

### C-005 实验任务：`CadLocatorBenchmark`（评审已定：先实测，后改码）

| 项 | 内容 |
|---|---|
| 输入 | **程序合成**的已知棱边图（ISO 12233 斜边 / 棋盘格 / 任意角度的直线段），棱边真值由生成参数给出 |
| 候选 A | 梯度剖面拟合（整数边缘两侧取灰度剖面，拟合极值位置） |
| 候选 B | 交点细化（对两条棱的交点做 `cv::cornerSubPix`） |
| 输出 | `pixel error` = 定位结果与真值之差，按**重复性**（σ）与**绝对偏差**（bias）分列 |
| 判据 | 是否达到 0.1~0.2 px（O-12 待定的那个数） |

**关键性质：该实验不依赖相机、不依赖 SDK、不依赖 CAD 模型** ——
输入是程序生成的合成图。因此 **C-005 的实验可以立即开始，不被 011 阻塞**，
也不受 O-8（SDK 未安装）影响。这一点评审未提及，但它是把 C-005 从"第二批"里
提前解锁的依据。

### 需一并决定的点（开放）

- **O-11**：SYS-15 §4 的误差预算在亚像素精度未达标前，是否要给出
  **"当前实际预算"**（用实测的量化误差代入）？否则 0.97 这个数字会被误读为已达成的余量。
  **建议：要**——这正是"0.000 残差"看起来很好、实为量化的成因。
- **O-12**：0.1~0.2 pixel 是 `CadStructureLocator` 的**性能要求**还是**目标**？
  若是要求，需在 ENG-10 §2.4 补入验收判据。**建议：要求**（否则预算的 3% 余量无法守）。

## C-007 失败任务的根因传递

**对应缺口**：Q-B15 · **严重程度 ★★★★★** · **第一批（必须）** · **状态：通过 + 引入 `FailureTrace`**

### 裁决结论

**终态错误必须携带首次失败原因**，而不只是最后一个被耗尽的状态。

实测（本次 M1 运行）：

```
终态 : FAILED（用时 403 ms）
错误 : code=0 (OK) MEASURE_SELECT 尝试次数已用尽（§7.3 上限 3），未能产出可用测量通道
```

真实轨迹：

```
SEARCH → TARGET_FOUND → ALIGN → STABILIZE → MEASURE_SELECT → CAPTURE
       → POSE_SOLVE → MEASURE_SELECT → CAPTURE → MEASURE_SELECT → FAILED
```

**真实根因**是"机型库未加载 → PnP 无法解算"。终态报的是**最后一个被耗尽的状态**，
与根因隔了三层回退 —— 现场按这条错误信息排查会直接查错方向。

### `FailureTrace`（评审修改 4）

```cpp
// src/data/FailureTrace.h（新增；纯数据，data 层）
struct StateTransition
{
    MeasurementState from;
    MeasurementState to;
    uint64_t         atNs;          // 单调时钟
    data::ErrorInfo  reason;        // code==0 表示"无错误原因"
};

struct FailureTrace
{
    MeasurementState           firstFailedState; // **首次失败所在的状态**
    ErrorInfo                  firstError;      // **根因**（首次失败的原因）
    ErrorInfo                  finalError;      // 终态（可能只是"预算用尽"这类症状）
    std::vector<StateTransition> history;       // 逐状态轨迹
    int                        rollbackCount = 0;
};
```

> **定稿说明（评审 v1.2）**：新增 `firstFailedState`（现场最需要的第一句话是
> "**哪个状态**先失败的"）；轨迹向量名取评审的 `history`。
> 评审给出的最终形态是：

```cpp
struct FailureTrace
{
    MeasurementState                 firstFailedState;
    ErrorInfo                        firstError;
    MeasurementState                 finalFailedState;   // v1.3 加入
    ErrorInfo                        finalError;
    std::vector<StateTransition>     history;
};
```

> **v1.3 定稿（2026-09-23 实施时修订）**：上面这个 5 字段形态即为实现的形态
> （`src/data/FailureTrace.h`）。相对 v1.2 的两处变化：
>
> | 变化 | 依据 |
> |---|---|
> | **删** `rollbackCount` | 实测**零消费者**（全工程没有任何地方读它）；且它的值可由 `history` 导出（触发失败的回退迁移条数）。一个无人读、又能从已有数据导出的冗余字段，只是多了一处互相漂移的机会 |
> | **加** `finalFailedState` | 只有 `firstFailedState` 而不知道终止在哪一步，回答不了"这套重试策略把它耗在了哪一段"。它与 `firstError` / `finalError` 构成"根因 vs 终点"的完整对照 |

### 填充点（⚠ v1.3 更正：**不是** `StateMachine::transition()`）

v1.2 原文写"`StateMachine::transition()` 是唯一迁移收口，在它内部追加一条
`StateTransition` 即可"。**实施时核实：这一条不成立**，两个实测原因：

1. **`StateTransition::error` 的语义是"导致这次迁移的错误"，而 `transition()`
   在成功迁移时拿不到它** —— 触发回退的错误此刻在
   `MeasurementController::lastError_` / `Recovery::error` 里
   （`handleFailure()`），`StateMachine` 对它不可见。
2. **"首次失败"在 `transition()` 里根本不可观测** —— 同状态重试
   （SYS-08 §7.3 的 `RETRY_IN_STATE`）**不产生任何迁移**
   （`applyRecovery()` 只置 `actionOpen_ = false`）。而
   `firstFailedState` / `firstError` 恰恰就是首次失败。

**实际实现**放在 `MeasurementController` 的**三个既有收口**上，
`StateMachine` **一字未动**：

| 填充内容 | 位置 | 为什么是它 |
|---|---|---|
| `history`（逐条 `StateTransition`） | `transitionTo()` | 全部迁移都经此，唯一收口；`from` 由迁移前的 `stateMachine_.state()` 给出，`error` 取挂起的失败原因 |
| `firstFailedState` / `firstError` | `handleFailure()` | 首次失败的天然观测点（本来就在写 `lastError_`）；判据 `failure.firstError.code == 0` |
| `finalFailedState` / `finalError` | `failWith()` | 入口处两个权威输入（`error` 入参 + 迁移前状态）齐备；且此处早于 `onEnteredState(FAILED)` 的释放 |

**"有唯一入口、无需到处插桩"这一性质仍然成立**：三个都是唯一收口，
不是散点插桩。层向上合法：application → data。

> ⚠ 一处**实施时发现的缺陷与修法**（v1.3 补充）：轨迹在 `failWith()`
> 里被填充，而记录包又是在**终态迁移之前**写的（必须如此 —— 终态迁移会
> 触发 `onEnteredState(FAILED)` 释放帧缓存，之后再写就拿不到统计量与质量）。
> 两者叠加的结果是：**盘上的 `history` 比 `result.json` 里声明的
> `state=FAILED` 少一跳**，同一份记录自相矛盾。
> 修法：新增 `MeasurementController::withTerminalHop()`，在写盘前对记录**副本**
> 追加那条终态迁移（用 `StateMachine::isLegalTransition()` 校验，不可达则不追 ——
> 编造一跳比缺一跳更糟）；**不写进 `failureTrace_` 自身**，避免与下一次
> `buildRecord()` 重复。

### 落盘位置（O-15 → 已定：`MeasurementRecord`，评审同意）

放 `MeasurementRecord`（C-002 新增的交付包），**不动冻结的 `MeasurementTask`**。
理由：根因是"交付与追溯"信息，与 C-002 的定位一致。

### 失败任务是否落盘（O-16 → 已定：**落，但不含原图**）

现状 SAVE 只在成功路径执行，故 FAILED 任务**不产生结果包**
（`MeasurementController.cpp:869` 注释明示）。若不落盘，根因没有载体。故：

| 项 | 成功包 | **失败包**（v1.3 实测形态） |
|---|---|---|
| `result.json` | 有 | 有（`state=FAILED` + **`failure` 摘要块**） |
| `failure.json` | 无 | **有**（摘要 + `history[]` 全量轨迹） |
| `config_snapshot/` | 有 | 有（排查需要） |
| `calibration_id.txt` / `turntable.json` | 有 | 有 |
| **raw 原图** | 有（最佳帧三路） | **无** —— 失败时未必有可用帧，且失败会频繁发生，落盘会淹没磁盘 |
| 保留策略 | 按任务 | ⚠ **本批只落盘，不轮转**（见下） |

**为什么拆成两个文件**：`result.json` 是**交付物**，读者要一眼看到根因；
`failure.json` 是**排查件**，轨迹可长可短且只有排障时才需要遍历。
两个文件都写摘要，但只有 `failure.json` 带 `history[]`。

**为什么"不轮转"**：轮转需要"保留数量/保留天数"这类配置项，而
ENG-09 §6 没有这类键、ENG-10 §5.3 也没有对应的缺省处置 ——
现在做等于凭空发明一套配置。**已登记为独立开放项**（需先有配置项承载）。
失败包不大（无原图），本批先落盘即可。

**理由**：现场最需要的不是一句"模型缺失"，而是

```
SEARCH OK → TARGET_FOUND OK → POSE_SOLVE FAILED / 5001 机型库未加载 / fallback 2 次 → FAILED
```

本轮已修的相关缺陷：`MeasurementStrategy` 的 `TARGET_FOUND` 分支原先会**丢弃**
调用方上报的 `deviceError.message`（见 `D-2`）—— 那是同一类问题的另一处。

> ⚠ **一处必须写下的实施风险**：失败包自身的写盘失败**只能记 note**，
> **不得再触发 `handleFailure()`** —— 否则"失败 → 落盘失败 → 失败"会无限递归。
> 该递归守卫已由一个既有用例（`落盘失败应在3次后终止且不进入COMPLETE`）
> 加上 `saveCalls == 4`（3 次尝试 + 1 次失败包）的断言钉住。

### 验收标准（v1.3：**已逐条实测通过**）

- 一个因机型库缺失而失败的任务，其错误信息中**同时**出现
  "机型库未加载（5001）"与"MEASURE_SELECT 用尽"；
- `failure.json` 中可按 `first_error.code` 检索、可按 `history[]` 复原完整轨迹；
- 失败包的目录**不含** `cam*.raw`。

**实测落盘实物**（`/tmp/aps_rec_failjson_*/measurement_123456789/`）：
`calibration_id.txt`、`config_snapshot/`、`failure.json`（1169 B）、
`result.json`（2329 B）、`turntable.json`（75 B），**无** `cam*.raw`；
两份 JSON 均可被 `cv::FileStorage` 正常解析；`first_error` = 5001、
`final_error` = 9002（"根因 vs 症状"两者同时在场）。

> ⚠ **该实物里的 `config_snapshot/` 是空目录** —— 这不是缺陷，而是**探针构造**所致：
> 驱动它的探针把 `configDir` 指到了一个不含 yaml 的临时目录，于是 7 个文件全部
> "缺失"。`Recorder::writeConfigSnapshot` 对缺失的处置是**非致命**的（返回 true、
> 只把缺失清单写进 `lastErrorText()`）。已另跑探针分开验证：真实 `configDir`
> → **7/7** 拷贝成功且 `lastErrorText()` 为空；空 `configDir` → 0 文件、`save()`
> 仍返回 1。**生产路径正确**；暴露的是测试覆盖缺口，登记为
> [§5.1 N-6](待裁决问题汇总.md)。

## C-008 非有限姿态值的处理边界

**对应缺口**：[C-02 §12.5 第 5 条](V2.1-C02_实施设计说明.md)（`PoseValidator` 对 NaN 是盲的）· **严重程度 ★★★★** · **状态：通过并已实施（v1.3）**

### 裁决结论

`PoseValidator` 必须**先**把非有限值（NaN / ±inf）拦下并给出**分类**，
而不是让它走进阈值判据。

### ⚠ 实施时的核实：NaN 盲区比裁决描述的**更窄，也更宽**

v1.2 的描述是"`PoseValidator` 对 NaN 无防护"。实测后要分开说：

| 量 | v1.2 描述 | 实测 |
|---|---|---|
| `reprojectionError` | 无防护 | **已有**一道 `isfinite` 检查（在判据 ② 内） |
| `inlierRatio` | 无防护 | **已有**夹取（`confidence()` 与 `validate()` 都做了 `isfinite ? ... : 0.0`） |
| `confidence` | 无防护 | 上一条的导出量，随之受控 |
| **`yaw` / `pitch` / `roll`** | 未提及 | **完全没有任何检查** |
| **`aircraftToShip` 的 12 个元素** | 未提及 | **完全没有任何检查** |

所以真正没拦的是**后两类**。而且它们不是"理论上的"漏洞 ——
可达路径是"yaw = NaN 的姿态一路走到 SAVE 并落盘"，落盘侧只能靠
`non_finite_fields` 点名表兜住（`num()` 把 NaN 写成 0），
那是**最后一道**防线。

为什么单靠阈值判据拦不住（三个理由，缺一这条闸门就会被绕开）：

- ⑤ 的 yaw 区间判据默认**根本不生效**（`yawMin == yawMax == 0` 是"未配置"哨兵），
  此时 `yaw = NaN` 连比较都不做；
- 即便配置了区间，`NaN < min || NaN > max` **恒为 false** —— NaN 以"通过"告终；
- `pitch` / `roll` 连判据都没有。

### ⚠ 一处偏离：闸门位置是**① 之后**，不是"最前"

裁决原文写"最前（早于 ①②③④⑤ 全部判据）"。实施时改为
**在 ① 之后、其余全部阈值判据之前**，理由是：

`success == false` 时这些字段**按冻结文档本无意义**（ENG-09 §5.24：
"false 时其余字段无意义"）。对无意义的字段做有限性检查，会把
"解算失败"这个**真实原因**覆盖成一个由垃圾值引发的 `NON_FINITE_VALUE` ——
而两者的处置方向完全不同：前者是"算法没解出来"，后者是"算出来一个不是数的东西"。

闸门放在 ① 之后，判定力**没有任何损失**：① 通过意味着字段是有意义的，
此时该拦的一个都不会漏。

### 判据覆盖范围（**不多不少**）

`ShipPoseResult` 的**全部**浮点量：`aircraftToShip` 的 9 个旋转元素 +
3 个平移元素 + `yaw` / `pitch` / `roll` / `reprojectionError`。
`success` 是 bool；`inlierRatio` 已在上面被夹到 [0,1]。

### 连带删除：判据 ② 内的重复检查

判据 ② 内原本另有一道 `!std::isfinite(result.reprojectionError)`。
闸门检查的是**同一个字段**且执行更早，故 ② 处**删除** ——
留着就是同一件事的第二份判据，两处迟早不一致
（改了一处忘了另一处，而两者都"看起来正常"）。

### `PoseValidationReason`

```cpp
enum class PoseValidationReason { OK = 0, NON_FINITE_VALUE };
```

**只登记裁决给出的取值，不发明未裁决的分类。** 其余不合格原因继续由
`reprojectionError` / `inlierRatio` / `confidence` 三个**数值**表达
（"差多少"比"属于哪一类"信息量更大）；凭想象切分"阈值未过"一类，
等于凭空发明一套 ENG-09 §5.27 表外的分类。

⚠ `OK` 取 0 而**不是**"未设置"：本枚举不是错误码表
（ENG-09 §5.27 的 `code == 0` 才是"未设置"），且
`PoseValidationResult{}` 的默认 `valid` 已是 false ——
若把 0 记作"未设置"，一个默认构造的结果会同时是
"valid=false"与"reason=未设置"，读者得不到任何信息。

### 落盘

`result.json` 的 `validation` 块增 `reason` 字段（名 `"OK"` / `"NON_FINITE_VALUE"`），
便于离线按原因筛选。名称映射在 `Recorder.cpp` 的 `validationReasonName()`。

> ⚠ 这是**第二处**枚举→名称映射（别处已有 `stateName` / `roleName`）。
> 已登记：本工程需要一处集中映射，否则每个枚举都会长出自己的第二份。

### 验收标准（**已实测**）

- 分别把 `yaw` / `pitch` / `roll`、变换矩阵的 9 个旋转元素、3 个平移元素
  置 NaN 与 ±inf，断言 `valid == false` **且** `reason == NON_FINITE_VALUE`；
- **反向判据（防止 reason 退化成常数）**：普通阈值未过时
  `reason == OK`；
- **顺序判据**：`success == false` 且 `yaw = NaN` 时必须给
  `OK`（而不是 `NON_FINITE_VALUE`）—— 见上文偏离说明。

**变异检查（先红后绿，已执行）**：

| 变异 | 结果 |
|---|---|
| M20 整个撤掉闸门 | NaN 的 yaw/pitch/roll **通过验证**，新用例转红 ✓ |
| M21 闸门只查 `rotation(0,0)` | 矩阵其余元素被放行，新用例转红 ✓ |
| M22 `reason` 恒为 `NON_FINITE_VALUE` | 反向判据转红（阈值未过被误报为非有限值）✓ |

三者还原后源文件与备份**逐字节一致**。

## C-013 `validate()` 的 bool 语义与对账（**已实施 2026-09-24**）

### 裁决结论

1. **契约**：`IPosePipeline::validate()` 的返回值 **≡** 它写入的 `out.valid` **≡**
   "是否通过全部判据"。它**不是**"验证过程是否执行成功"。
2. **对账分支**：若实现返回的 bool 与它自己写入的 `out.valid` **不一致**（= 违背契约），
   控制器必须**可见地 FAILED**（码 `kErrStateFailure`，消息点出两个值），
   **不得静默按任一方继续**。
3. **验证详情无条件留存**：`validationResult_ = validation` 必须在**整段最前**，
   包括对账分支之前。
4. **接口注释**：`IPosePipeline::validate` 补 `@return` 说明（该接口此前**没有任何
   `@return`**，是歧义的源头；紧邻的 `solvePose` 有明文，两者语义不同）。
5. **不动任何签名** —— 本裁决**不涉及 IF-SW-02**。

### 来源与缺陷

全仓静态审查报告 `proj_plane_review_9775ea6.md` 的 **R05**（基线 `main@9775ea6`）。
`MeasurementController::stepValidate` 原写作 `if (!pipeline_.validate(poseResult_, validation))`，
把"判不合格"读成"验证过程失败" → `handleFailure` → **提前 return**，
使 `validationResult_ = validation` 与 `strategy_.excludeCamera(...)` **两步都执行不到**。
真实 `PoseValidator` 判不合格就返回 `false` ⇒ **生产路径必然踩中**；
而测试桩**恒 `return true`**，所以这条断点从未在任何测试里出现过。

### ⚠ 实施中核实出的、与设计意图不符的一处（本裁决的实质更正）

设计稿写的是"把 `validationResult_ = validation;` 提到**分支之前**"，而"分支"指的是
`if (!validation.valid)`。实施时若照字面放在**对账分支之后**，就会在**新的失败通路上
原样复现 R05 要修的缺陷** —— "验证过程出问题时，验证详情反而最不可得"。
故裁决第 3 条把位置钉死为**整段最前**，理由有二：
① 契约被违背时，实现到底报了什么（`reprojectionError` / `inlierRatio` / `confidence`）
**正是定位该实现哪里坏了的唯一线索**，丢掉它会让对账分支只剩一句"true ≠ false"；
② 只**存**不**用** —— 下面的分支仍以"除 `out.valid` 外无任何动作"为前提，
故保存一个自相矛盾实现写出的结果**不会污染任何控制流**。

### 落地方式

| 位置 | 改动 |
|---|---|
| `src/application/MeasurementController.cpp`（`stepValidate`） | 契约注释 + 无条件留存（最前）+ 对账分支；`if (!validation.valid)` 分支**逐字保留**（保住 C-006 的"回退是非错误的处置动作"与用例 3 的 tick 轨迹） |

### v1.6 更正（对账分支改为**直接终止**；v1.5 的实施与裁决结论不符）

**本裁决的"裁决结论"一字未改**，改的是 v1.5 的**实施**：裁决第 2 条写的是"必须**可见地

  回退则是拿一个自相矛盾的实现继续跑完测量 —— 那正是"不得静默按任一方继续"要防的事。
- **测试的更锋利之处**：桩由"持续违约"改为 `validateLieTimes`（**只违约一次**），用例**逐拍驱动**。

- **变异**：`failTerminal` 换回 `handleFailure(kErrTransient)` ⇒ 该用例必转红（先红的是
  "未当次 FAILED"这一条）。

## C-014 install 规则的落点与安装自检口径（**已实施 2026-09-24**）

### 裁决结论

1. **`install(TARGETS)` 写进建立 target 的那个函数/文件里**，不集中写、也不各自抄一份：
   `src/CMakeLists.txt` 的 `aps_add_module_library()`（10 个模块库）、
   `src/app/CMakeLists.txt`（可执行文件）。
2. **安装断言写在 `install(TARGETS)` 的同文件、且排在其后**（`install(CODE ...)`，
   在 `cmake --install` **内部**执行）。
3. **自检覆盖 `bin/` 与 `lib/` 两侧**：只断言 `bin/` 会漏掉 R02 缺陷的一半
   （报告原文就是"没有 bin/、没有 lib/"）。
4. **新增 `install_launch_check`：从安装目录真的启动一次**，判据是**退出码 124**
   （`timeout 3` 把它杀掉 = 事件循环起来了，即 README §1 的 010 实测口径）。
5. **不按库型设条件** —— SHARED 下该测试必然红这一事实**登记**进既有 **H-10**，
   不用条件把它藏掉（`CompilerOptions.cmake` 的 `CMAKE_SKIP_INSTALL_RPATH ON` 是
   **有意**的：离线交付不能带开发机路径）。
6. **不新增 `cmake/InstallCheck.cmake`** —— 新增文件要同步升版 ENG-03 §5，
   会把本批的文档升版从 2 份推到 3 份，超出已裁范围。

### 来源与缺陷

审查报告的 **R02**：全工程 `install(TARGETS ...)` 实体 **0 处**（7 处 `install(`
全是 `install(DIRECTORY`），`deploy/` 因此只有空的 config/models/calibration，
**没有 bin/、没有 lib/**；而原 `install_check` 只跑 `cmake --install`、**不校验任何产物**，
所以这个缺陷不被任何检查覆盖。`cmake/InstallRules.cmake` 文件头声称分工是
"各模块 → 各自的 `install(TARGETS ...)`"，但**那个约定从未实现** ——
约定写了不等于做了，故该段现在只描述代码里**实际存在**的分工。

### 为什么写进 `aps_add_module_library()` 而不是各模块

技术论据比"少写 10 遍"更强：**该函数是唯一知道"这个 target 是否存在"的地方** ——
它对空模块直接 `return()`（此刻 `add_library` 未执行）。若写在各模块文件里，
每个都要自己再判一次 `if(TARGET ...)`，漏一个就是配置期直接报
`install TARGETS given target "data" which does not exist` —— 把"这个模块还没写"
变成"整个工程配置不过"，正是该函数三条设计要点要避免的事。
也不违反 InstallRules 文件头那句"不集中写"的**理由**：`include(InstallRules)`
早于 `add_subdirectory(src)`，那时无任何 target；而宏内恰好在 target 刚建立之后执行。

### 两条必须记住的陷阱（均已实测）

1. **父目录自己的 install 规则全部排在子目录 `include()` 之前**，与
   `add_subdirectory()` 出现的位置无关。故"断言某个 target 已装好"的 `install(CODE)`
   写在 `cmake/InstallRules.cmake` 里会在 `bin/` 被拷贝**之前**执行，**必然失败**。
   （已在 3.31 实测：InstallRules 的 CODE 在第 75~96 行，子目录 `include()` 在第 102 行。）
2. **转义**：`${CMAKE_INSTALL_BINDIR}` 配置期展开（不转义）；
   `\${CMAKE_INSTALL_PREFIX}` 与 `\$ENV{DESTDIR}` 安装期读取（须 `\$` 转义）。
   另一侧是反直觉的：**裸 `$?` 不会**被 CMake 展开（只有 `${…}` / `$ENV{…}` /
   `$CACHE{…}` / `$<…>` 才是变量引用），故 `\$?` 的转义**不是必需的**，
   只是把"这是给 sh 的"写明白。⚠ 本条注释起初断言"不转义会被展开成空串、
   测试退化为无脑通过"，**那是错的**，已改正。

### 落地方式

| 位置 | 改动 |
|---|---|
| `src/CMakeLists.txt` | 宏内加 `install(TARGETS ...)`（ARCHIVE/LIBRARY → lib、RUNTIME → bin）；新增全局属性 `APS_INSTALLED_LIBRARY_TARGETS`（**与 `APS_CREATED_MODULES` 刻意分开**：后者含 INTERFACE 聚合模块，混用会让断言去找不存在的 `lib<聚合名>.a`） |
| `src/app/CMakeLists.txt` | `install(TARGETS AircraftPoseSystem RUNTIME ...)` + 紧随其后的 `install(CODE ...)` 断言（bin/ 存在且可执行、lib/ 下**每个**已建立模块库都在），期望文件名在**配置期**算好烘进 CODE |
| `cmake/InstallRules.cmake` | §分工改写为如实的三方分工；新增 `install_launch_check`，并用 `FIXTURES_SETUP`/`FIXTURES_REQUIRED`（而非 `DEPENDS`）—— fixture 的 setup 测试即使 `ctest -R` 也会被自动带上；`WORKING_DIRECTORY` **必须显式设为安装前缀** |
| `README.md` | §2 安装节 + §4.6 新增第 6 条约定（三方分工表 + 两个陷阱） |

**自检前缀固定为 `${CMAKE_BINARY_DIR}/install_check`，不是 `deploy/`** ——
后者是真实交付树，若自检指向它，一次 `ctest` 就会覆盖交付内容。

### ⚠ 实施中核实出的一处（`WORKING_DIRECTORY` 不设则恒红）

`install_launch_check` 首次运行 0.02 秒即失败。根因**不在安装规则**：本程序**默认按
当前工作目录**解析配置目录（`main.cpp` 的 `configDir` 初值为 `"config"`），而 ctest 的
默认工作目录是 `CMAKE_BINARY_DIR`，那里没有 `config/` ⇒ 程序以**退出码 1** 打印
"找不到配置文件"后退出。实测：cwd = 安装根 → 124；cwd = `bin/` 或 `build/` → 1；
任意目录 + `argv[1]` 指定配置目录 → 124。
**取"cwd = 安装根 + 默认配置路径"**，因为那正是现场解包后的动作
（`cd deploy && ./bin/AircraftPoseSystem`）。
⚠ 顺带更正一处**被夸大的说法**：`argv[1]` **确实**可以指定配置目录（故程序并非只能从
包根启动），但 `models/`、`calibration/`、`logs/`、`output/` 仍按 CWD 解析 ——
已并入 [汇总 Q-B10 的补充](待裁决问题汇总.md)，不是一个洞的补丁。

### 验收标准

- 手工 `cmake --install` 后 `bin/AircraftPoseSystem` 存在且可执行；自检打印
  `…/lib 下 10 个模块库齐备`（**不是 9 个** —— `device` 是三个库；
  曾误报 `libdevice.a` 缺失，属我把聚合目标当成了实体库）；
- `ctest -R install_check` / `install_launch_check` 均绿；
- **变异对照**：去掉 `src/app` 的 `install(TARGETS ...)` → `install_check` 必转红；
- ⚠ **变异检查的一条纪律**：`cp -p` 还原会**保留备份的 mtime**，
  make 因此认为源文件比目标文件旧而**跳过重编译** —— "还原后转绿"那一臂会测到**陈旧二进制**。
  必须 `touch` 后再构建。同理，CMake 文件用 `cp -p` 还原后须**显式重新 configure**
  （`cmake -S . -B build`），否则生成的 `cmake_install.cmake` 仍是变异版本。

**裁决结论一字未改**（第 4 条"新增 `install_launch_check`"仍然成立），改的是它的**判据强度** ——

## C-015 A1 数据契约批：取帧结果／原始载荷／身份绑定与触发执行路径（**已实施，2026-09-26**）

### 裁决结论

**把"一次取帧失败"的三个层面分开承载**，并让每个层面各自可读、可测：

| 要表达的事 | 载体 | 变化时机 |
|---|---|---|
| **设备就绪状态** | `data::DeviceState`（既有枚举，`ICameraBackend::state()`）**新增 `DISCONNECTED`** | **仅**在 `OpStatus::Disconnected`（SDK 码 `-118` 等**注释明确**者）时置位；超时／无帧／未就绪**都不**置位 |
| **本轮取帧结果（每路 + 聚合）** | 新类型 `CaptureRound`（每路 `attempted`／`skippedReason`／`GrabResult`／时间戳／触发 ＋ `capturedCount`／`succeeded`／`aggregate`／`startedNs`／`finishedNs`），经 **`IMultiCameraManager::lastCaptureRound()`（纯虚）** 读取 | 每次 `capture()` **覆盖**一次 |
| **测量处置**（等待／降级继续／终止） | 既有 `degradationNotice_` / `handleFailure` 路径 | **决策一字不改**，只改**原因文本来源** |

**另外三条同时成立的契约**：

1. **原始载荷**：`ImageFrame` 新增 `raw`（`RawImagePayload`）／`captureFormat`／`rawPolicy`
   三个字段。`rawPolicy` 与 `captureFormat` **交叉一致**（`RawOptional` 仅限 8 位格式；
   有效位深 > 8 者必须 `RawRequired`），矛盾即契约错误 —— 这条正是"虚拟 8U 帧"与
   "真实 Mono12 帧丢失载荷"**必然分流**的判据，不需靠文件名、逻辑 `cameraId` 或重查配置去猜。
   **布局**：本批**声明紧凑契约**（`Mono8`／`Mono12`／`BGR8` ＝ 1／2／3 字节每像素、
   无行尾填充、无整帧填充），**再用长度等式校验输入**（`compactSizeMatches`，
   ⚠ 该名字**不得**改成"布局已确认"：一次字节数比较只能说明"长度与紧凑契约相容"）。
   **`Mono12` 的显示转换按 PFNC 实现**（低位对齐、`>> (12 − 8)`），依据＝
   该 SDK 的格式码**逐位等于 EMVA GenICam PFNC 的格式码**（实测 `0x01100005` ＝ PFNC `Mono12`），
   ⇒ 这是本批**唯一**一处"由标准推实现"，故**只实现、不记已验证**：实机核实的是
   "本台设备的输出符合该约定"，核实否**只改这一处实现**。
2. **取帧结果与诊断出口**：`ICameraBackend` 的 `initialize`／`start`／`stop`／`close`／
   `setTriggerMode`／`triggerSoftware` 六方法返回 `OperationResult`，`grab` 返回 `GrabResult`
   （**只有一个权威状态字段** `OpStatus`，默认 `Unset` **不表示成功**）。
   `SdkFailure{call, code}` **必须同时带操作名与原码** —— 同是 `-119`，
   `GetFrame` 超时与 `ReleaseFrame` 超时是完全不同的故障。
   **`sdkError` / `cleanupError` 分开**：主操作成功而**必要清理失败**（`GetFrame` 成功、
   `ReleaseFrame` 失败）⇒ **整体失败且不交付帧**（不能把"资源没还回去"说成成功）；
   已有主失败时清理失败**只进 `cleanupError`、保留首因**。
   **顺序是硬性的**：先判"调用是否失败"，**再**判"帧是否可用" ⇒ `IMV_OK` 但帧不可用是
   **`CorruptFrame`**（`sdkError` 仍记 `{GetFrame, IMV_OK}`），**绝不算超时**。
3. **身份绑定与触发**：`role`（配置／装配）／逻辑 `cameraId`（配置）／设备型号与序列号
   （**SDK 枚举回报**）**三栏分开**；按**序列号精确匹配**打开（空序列号 ⇒ 明确失败，
   **不取"第 0 个设备"**）；匹配到 0 个或**多个** ⇒ 明确失败并把枚举结果列进错误信息。
   `triggerMode` 由 `bool` 扩为三值 `CameraTriggerMode{FreeRun, Software, Hardware}`，
   **读回必须读到三项**（`TriggerSelector`／`TriggerMode`／`TriggerSource`）——
   只读 `TriggerMode` **分不出软触发与硬触发**（两者都是 `"On"`）；读不全 ⇒
   `reported` 置 `nullopt`、`consistent = false`，**不得**默认成某个合法模式。
   **软件触发的发令者只有 `MultiCameraManager` 一个**（后端只取帧、**绝不**发令）：
   一次 `capture()` 内 `IMV_ExecuteCommandFeature` 与 `IMV_GetFrame` **各恰好 1 次**；
   **发令失败 ⇒ 取帧次数为 0**（不得"失败也照样去等一帧"）。

### H-001 双时间戳语义 —— **已满足，不改名，补契约测试**

评审要求冻结：

```cpp
ImageFrame { uint64_t hostTimestampNs; uint64_t deviceTimestampNs; }
```

**核实结果：该语义在代码里已经冻结，且比提议更细**（`src/data/ImageFrame.h`，
依据 ENG-09 §2.5 + 裁决 C-01，含完整理由注释）：

| 现有字段 | 语义 | 与评审提议的关系 |
|---|---|---|
| `timestampNs` | **主机单调时钟**（`CLOCK_MONOTONIC`），采集线程在 `grab()` 返回后打点；同步校验的**唯一**基准 | 即评审的 `hostTimestampNs` |
| `deviceTimestampNs` | 相机 SDK 上报的相机内部时间戳，不可用时 0；**仅**用于诊断跨相机时钟偏移 | 与评审一致 |

**裁决：不把 `timestampNs` 改名为 `hostTimestampNs`。** 理由：

1. 该字段名是**裁决 C-01** 冻结的（合并 SYS-05 §5.1 / ENG-02 §4.1 / ENG-04 §4.1
   三份文档字段不一致的并集），改名的收益只是措辞；
2. 改名要动全部写入点，而**语义一个字都没变**——纯风险无收益；
3. 该文件注释已明确写出"禁止用墙钟做同步判断"的理由（NTP 校时可向后跳变），
   即评审担心的"三相机同步后返工"**在类型层已被防住**。

**但评审的担心有一个真实缺口**：字段语义正确，**没有任何东西强制后端填对**。
故补两项（成本极低）：

| 补充 | 内容 | 状态 |
|---|---|---|
| 契约测试 | Virtual 相机下断言 `timestampNs` **严格单调**（同通道连续帧）；`deviceTimestampNs` 为 0 或"非 0 且单调"，**不得**等于主机时间 | 评审已确认，**必须写进测试**（不得只写在文档里） |
| 真机验收 | 011-A1 验收项：若 SDK 不提供设备时间戳，**必须恰为 0**，不得用主机时间冒充（冒充会让"跨相机时钟偏移"诊断永远给出 0，看起来完美） | 评审已确认，**必须写进测试** |

> 评审原文的措辞值得原样保留：**"禁止 `deviceTimestampNs == timestampNs`"** ——
> 这是一个可以用一行断言表达、却能挡住一整类"看起来正常"的缺陷的判据。

```
A. C-02   bestFrame 数据链实施        ← 设计见 V2.1-C02_实施设计说明.md（待批准）
        ↓
B. C-006 / C-007  错误码 + FailureTrace
        ↓
C. 010.5  CadLocatorBenchmark        ← C-005 的**实验**，不改算法
        ↓
D. 011-A0 SDK 适配准备               ← 改 FindImvSdk.cmake + 能编译 + 能枚举
        ↓
E. 011-A1 真实相机采集
```

**排序理由**（评审）：数据链问题（A）**优先级高于真实 SDK**（D）——
拖到真机之后会连带影响 raw 保存、结果追溯与测试；错误码与根因（B）要在真机排障之前就位；
C-005 的实验不依赖相机 / SDK / 转台 / CAD，故提级为独立的 **010.5** 阶段。
